## [API-01] BLOCKER — FD 복제 리다이렉트 하나로 읽기 전용 명령이 소스 쓰기로 오판된다

### 근본 원인 — 짚었던 곳이 아니었다

감사는 `bashwrite.ts` 의 리다이렉트 정규식을 의심했다. **틀렸다.** 그 정규식은 이미 fd 복제를
대상에서 빼고 있었다(`redirectTargets` 안의 `if (amp && /^\d+$/.test(t)) continue`).

새던 곳은 **세그먼트 분해**였다. `SEGMENT_SPLIT` 이 `&` 로 명령을 쪼개므로 `cat src/app.ts 2>&1` 이
`cat src/app.ts 2>` 와 **`1`** 두 조각이 된다. 뒤 조각의 머리 `1` 은 `READ_ONLY_HEADS` 에 없으니
[SEC-B1] 의 「모르는 명령은 쓸 수 있다고 본다」 규칙에 걸려 `mutating = true` 를 세우고, 그러면
「대상이 없을 때 언급을 본다」 안전망이 발화해 **명령 전체의 경로 언급**이 판정으로 간다.

같은 뿌리에서 셋이 더 나왔다:

| 트리거 | 왜 |
|---|---|
| `2>&1`·`1>&2` | `&` 분해 → 가짜 세그먼트 `1` (위) |
| `cd X && <읽기>` | `cd`·`pushd` 가 `READ_ONLY_HEADS` 에 없다(`popd` 만 있었다) → 접두 한 조각이 명령 전체를 변형으로 만든다 |
| heredoc 본문 | 개행이 분해 기준 → 산문 한 줄이 세그먼트가 되고 첫 낱말이 「모르는 명령」이 된다 |
| 승인 문구 언급 | 세 자기해제 가드가 `invokesHarness(cmd) && /\bgate\b/ && /\bapprove\b/` 를 **명령 전체에서 따로따로** 평가했다 |

`[EFF-289]` 주석이 `test`·`true` 에서 **정확히 같은 증상**을 이미 고쳤다는 점이 중요하다 —
이건 새 버그가 아니라 **같은 부류의 미완결**이다.

### 무엇을 어떻게 고쳤나

1. **`core/src/bashwrite.ts` — `maskNonCommandText()` 신설.** 스캔 전에 「명령이 아닌 구간」을
   **같은 길이의 공백으로** 덮는다(길이 보존이 필수다 — 리다이렉트 위치로 그 자리의 가상 cwd 를
   찾으므로 길이가 달라지면 `cd` 추적이 통째로 어긋난다). 덮는 것은 둘뿐이다:
   fd 복제 리다이렉트(`N>&M`·`>&-`), 그리고 **데이터 싱크에 먹이는 따옴표 heredoc 본문**.
   - 안전을 위해 두 겹으로 좁혔다: 소비 명령이 `HEREDOC_DATA_SINKS` 화이트리스트에 있고
     **구분자가 따옴표로 닫힌** 경우만. `sh <<EOF … EOF` 처럼 **실행되는 본문은 그대로 본다.**
2. **`core/src/bashwrite.ts` — `READ_ONLY_HEADS` 에 `cd`·`pushd` 추가.** cwd 추적은
   `segmentsWithIndex` 가 별도로 하므로 이 목록과 무관하다.
3. **`core/src/hook.ts` — `runsHarnessWith()` 신설.** 자기해제 세 가드(`gate approve` ·
   `phase --force` · `doctor --accept-policy`)를 **「하네스를 실행하는 명령줄」 안에서** 판정한다.
   `commandLines` 가 이미 따옴표를 벗기고 `sh -c`·`eval`·`xargs`·`find -exec` 안쪽을 풀고
   `time`·`sudo`·`npx`·경로 접두를 벗기므로, **그 줄의 머리가 하네스인지**만 보면 실행과 언급이 갈린다.

### 고치다가 한 번 열었고, 기존 테스트가 잡았다

줄 기반으로 좁히자 `` echo `harness phase set P7 --force` `` 가 **통과**했다. 백틱은
`SEGMENT_SPLIT` 기준이 아니라 인자 안에 통째로 남아 머리가 `echo` 로 보였는데, 실제로는
명령치환이라 **그 명령이 실행된다.** `hook-pre-tool.test.ts` 의 「백틱 안 형태를 막는다」가
이것을 잡았다 — 그 테스트가 없었으면 조용히 나갔다.

닫은 방법: `harnessInvokingLines` 가 백틱과 `$(…)` 스팬을 뽑아 재귀적으로 명령줄로 편다.
**이 케이스를 새 회귀 테스트에도 못 박았다.**

### 계약 변경 (사용자 확인 필요)

`policy.test.ts` 에 **「인용부호 안의 언급도 막힌다 — 의도된 과차단」** 이 계약으로 고정돼 있었고,
근거는 **「방향을 좁히면 `bash -c "..."` 가 열린다」** 였다. 그 전제가 실측으로 반증됐다 —
좁혔는데도 우회 20종(`bash -c`·`eval`·백틱·`$()`·`xargs`·개행·접두·절대경로·코어 직접 호출 포함)이
전부 계속 막힌다. 그래서 계약을 **「실행은 막고 기록은 막지 않는다」** 로 바꿨다.

바뀐 것: `echo "run harness doctor --accept-policy" >> README.md` 가 deny → **allow**.
안 바뀐 것: 명령치환은 인용부호 «안»에 있어도 실행이므로 계속 deny.

**이건 보안 계약의 변경이라 사용자 판단 항목으로 올린다.** 근거는 이 문서와
`evidence/probe-approve.js`(20 우회 × 7 정당 명령) 다.

### 회귀 테스트

`core/test/overblock-2026-08-27.test.ts` — 12 케이스. **두 방향을 함께** 고정한다:
막히면 안 되는 것(순수 조회·문서 작성)과 막혀야 하는 것(소스·코어 쓰기 14종, 자기해제 24종).
한쪽만 고정하면 다음 사람이 과차단을 고치다 차단을 열거나 그 반대가 된다 — 이번 라운드에서
실제로 한 번 일어났다.

## [OPS-01] BLOCKER — 저널 손상이 state 가 멀쩡하면 사용자 인터페이스 어디에도 안 보인다

### 근본 원인

`degraded` 신호가 **한 경로에만 배선**돼 있었다 — `readState` 의 `catch` 안에서만 설정된다.
즉 state.json 이 정상이면 **저널을 아예 열지 않고**, 그래서 손상이 배너·deny 사유·Stop 가드
어디에도 나타나지 않는다. 사용자가 스스로 `harness doctor` 를 돌리지 않는 한 —
그렇게 하라고 알려 주는 것도 없이 — 몇 주가 지나도 감사 저널이 깨진 줄 모른다.

### 무엇을 어떻게 고쳤나

`core/src/hook.ts` — 정상 경로에서도 저널 건강을 보되 **세션 시작에서만** 본다. 매 도구 호출마다
15MB 저널을 파싱하면 이 제품이 파는 「훅은 단일 밀리초」가 무너진다. 세션당 한 번이면 배너에
실려 사용자에게 도달한다.

`Degraded` 에 `stateDamaged` 를 더해 **두 이야기의 문구를 갈랐다**: 「지금 재생으로 돌고 있다」와
「상태는 정상인데 감사 이력이 깨졌다」는 사용자가 할 일이 다르다.

### 회귀 테스트 · 재측정 · 변이 검증

`core/test/observability-2026-08-27.test.ts` §OPS-01 — 4 케이스(대조군 · 저널만 손상 ·
여러 줄 · state 와 겹칠 때 문구 구분). 변이(세션 시작 검사 비활성화) 시 2건 red 확인, 원복 확인.

## [OPS-02] BLOCKER — 번들이 없으면 강제가 조용히 꺼지는데 `doctor` 는 `ok: true`

### 근본 원인

`core/dist` 가 없으면 훅 경로는 무해 계약대로 조용히 exit 0 한다 — **그 자체는 옳다.**
결함은 그 사실이 **어디에도 안 남는 것**이었다. stderr 는 exit 0 이면 사용자에게 안 보이고,
`hook-errors.log` 는 `require` 가 실패한 뒤라 기록조차 되지 않으며, 제품의 유일한 자가 진단인
`doctor` 는 건강하다고 확인해 준다. 사용자는 설계 트랙인 줄 알고 소스를 마음껏 쓴다.

### 무엇을 어떻게 고쳤나

`bin/harness` 의 catch 가 `.harness/.runtime/hook-errors.log` 에 **한 줄을 남긴다**
(`no-bundle enforcement-off …`). dist 없이 도는 순수 node 코드라 이 경로에서도 동작한다.
`doctor` 는 **이미** 이 로그의 건수를 issue 로 올리고 있으므로(`doctor.ts` `countHookErrors`)
기존 배선이 그대로 받는다 — **새 통로를 만들지 않고 끊긴 곳만 이었다.**

기록 실패는 전부 무시한다(무해 계약: 로그를 못 남기는 것이 세션을 깨는 이유가 될 수 없다).

### 회귀 테스트 · 재측정 · 변이 검증

`core/test/observability-2026-08-27.test.ts` §OPS-02 — 4 케이스. 실제로 **dist 없는 설치본**을
만들어(부분 클론 흉내) 하위 프로세스로 구동한다: 훅 exit 0 유지 · 로그에 흔적 · CLI 는 exit 1 ·
**비참여 프로젝트에는 아무것도 안 쓴다**(비간섭 불변식). 변이 시 1건 red 확인, 원복 확인.

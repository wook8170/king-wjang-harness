판정

출하 가능 (GO)
한 번 되돌렸다가 근거를 세워 회복한 판정이다. 읽는 사람이 「open 37건인데 GO?」라고 물었고, 그 질문으로 목록을 다시 훑자 게이트 판정과 충돌하는 항목이 나왔다 — 그래서 47·48차에 판정을 조건부로 내렸다. 49차에서 그 항목들을 실측으로 처리하고 판정을 회복한다.
회복의 근거는 둘이다. ① 게이트를 실제로 깨던 3건을 닫았다(SHIP-02 · SHIP-04 의 문서 부분 · API-11). ② 절차에 없던 「게이트 × 잔여 전항목」 기계 대조를 신설해 13개 게이트를 전수 다시 봤다(99-final-verification.md §6) — 남은 37건 중 어느 것도 게이트 목표 문장을 깨지 않는다는 것을 항목별로 적었고, 전부 deferred + 언제·왜를 붙였다.
착수 시 차단 3건 · 적색 게이트 7개 · open HIGH 4건은 전부 닫혔다(라운드 1~3, 전건 회귀 테스트 + 변이 검증). 테스트 1404 → 1494, tsc 0.
50차에 하루 보류됐다가 51차 실측으로 다시 회복했다 — 그 우회도 지우지 않는다. 50차는 [API-04](HIGH·fail-open)를 닫은 근거인 「1.09MB=4.4s · 여유 2.3배」가 재현되지 않아 [PERF-08] 을 열고 판정을 멈췄다 — 그 회귀 테스트가 단독 반복 8회 중 3회 실패했고 1회는 훅 예산 10s 자체를 넘겼다(12549ms). 다만 측정 창이 오염돼 있었다: 세션 내내 load 1분평균 6→88(타 세션 vitest 2건). 50분을 감시해도 유휴 창이 열리지 않아 「결함이 아니라 측정 불가」로 남겼다.
51차에 창이 열렸다(load1m 3.82). 같은 테스트를 단독 8회, 매회 load 를 함께 적어 다시 쟀다 — 4037 / 4099 / 4444 / 4323 / 4149 / 4293 / 5992 / 4397 ms · 8/8 통과 · 중앙값 ~4.3s · 알람 8000ms 대비 여유 약 1.9배. 「4.4s」가 그대로 재현됐다. 50차가 본 실패는 load 50~88 구간의 것이었다 — 제품이 아니라 기계를 쟀다. [PERF-08] 을 기각하고(48차 [DEP-11] · 50차 [SEC-17] 과 같은 처리) GO 로 돌아온다. [API-04] 는 verified 유지.
그 소동이 진짜 결함 둘을 드러냈다. [PERF-09](LOW·open) — 이 회귀 테스트에는 같은 리포의 벤치가 가진 부하 창 판정(BUSY = load1m > cores × 0.5)이 없어 「제품이 예산을 넘음」과 「기계가 바쁨」을 구분하지 못한다. 감사자가 이것 때문에 50분을 태웠다. 부하 민감성은 실측으로 확인됐다 — load 3.9 에서 4037ms 이던 것이 load 5.3~6.0 에서 5992ms 로 올라 여유가 1.9배 → 1.33배로 준다. 처방이 양날이라(부하 창 skip 은 실패를 감추는 방향) v0.1.3 으로 연기한다. [UX-15](MED·verified) — 플러그인으로 설치되면 CLI 가 사용자 셸 PATH 에 없어 게이트 승인 안내를 사람이 복사해도 안 돈다. 사람만 실행할 수 있는 명령이라 게이트가 열리지 않는다. 안내를 런타임 절대 경로로 바꿔 닫았다.
게이트 목표 문장은 보류 중에도, 되돌릴 때도 손대지 않았다 — 움직인 것은 판정이지 기준이 아니다.
되돌렸다 회복한 이력을 지우지 않는 이유: 이 리포트의 값어치는 판정이 아니라 판정을 세우는 방식에 있다. 47차의 「GO 가 성급했다」는 지적이 없었다면 §6 은 없었을 것이다.

#조건어떻게 닫았나 (전부 measured, evidence/recheck-dep11-ship02.log)
㉠DEP-11 재검증 — G9 의 근거가 흔들린다DEP-11 은 감사 오류였다 → rejected. 문서대로 설치된 실기 HOME 의 캐시 4버전 전부 node_modules 66MB·73패키지를 갖고 있고 vitest 2.1.9·vite 5.4.21·esbuild 0.27.7 이 실재한다 — 축⑩ SHIP-04 와 일치. ㉡SHIP-02 — G3 와 충돌원 측정의 범위가 좁았다. harness 는 사용자 본인 셸에서만 PATH 에 없다 — 에이전트가 명령을 실행하는 셸에는 Claude Code 가 플러그인 bin/ 을 얹어 준다(실측). README 가 그 구분을 적지 않은 것이 결함이므로 4언어에 문단을 넣어 닫았다(청정 env 로 실측한 PATH 한 줄 포함). 같은 대조에서 G3 를 깨는 항목 둘을 더 찾아 함께 닫았다 — README:114 의 「Self-contained … 0 vulnerabilities」 문안(SHIP-04 문서 부분)과 MCP 스키마가 goal 을 선택이라 광고하고 거부하던 API-11.

장부 위생도 함께 고쳤다. open 36건을 전부 deferred + 언제·왜로 전환했다(v0.1.3 문서·공급망·관측성·UX 라운드, v0.2 입력 검증 계층). 이제 대장만 보고도 판정이 읽힌다 — open 0 · deferred 37 · rejected 2.

절차 자체도 고쳤다. 47차의 진짜 교훈은 「이음매 점검을 축끼리만 했다」이므로, 99-final-verification.md 에 §6 게이트 × open 기계 대조를 신설했다. 이 절이 이번에 세 건을 잡았고, 낡아서 게이트와 반대말을 하던 행(PERF-03)도 같은 절이 잡았다.

이 감사가 실제로 발견한 것 — 한 문단

강제 자체는 매우 강하다. 설계 트랙 소스 쓰기 우회 28/28 차단(축④) · 셸 쓰기 우회 30+ 형태 전건 차단(축⑥) · 저널·상태 파일 덮어쓰기 10/10 차단(오케스트레이터 프로브) · 이력 비밀 0/315 커밋 · 커밋된 core/dist 가 소스와 바이트 일치(세 축이 독립 확인) · 테스트 1404/1404 × 3회 동일(착수 시점) · tsc 0. 이 제품이 파는 「모델은 반환값과 논쟁할 수 없다」는 실측으로 성립한다.

무너지는 곳은 그 경계의 정밀도와, 경계가 사라졌을 때의 가시성이다. 정당한 명령의 약 25%(8/32)가 오차단되고 — 그것도 읽기 명령이 — 거부 사유는 사실과 다르다(「읽으려 했는데」 「바꿀 수 없다」고 답한다). 반대로 번들이 없거나 저널이 깨지면 강제가 통째로 멈추는데, 제품의 유일한 자가 진단이 건강하다고 확인해 준다. 훅 출력이 모델 컨텍스트로 들어가는 제품에서 틀린 사유는 에이전트를 잘못된 방향으로 민다.

이 감사에서 배운 것

1. 감사자가 제품에 막히는 것이 최고의 사용성 데이터였다. 계획된 11축 어디에도 「오케스트레이터가 제품에 막힌 경험」 항목은 없었다. 그런데 차단 결함 3건 중 1건과 HIGH 4건이 전부 거기서 나왔다. 도그푸딩을 사고로 얻었고, 사고가 축보다 많이 찾았다.

2. 같은 결함을 두 감사자가 독립 발견하면 심각도 판정이 단단해진다. 축②의 API-01 과 오케스트레이터의 ORCH-05 는 서로를 모른 채 같은 트리거를 찾았다. 한쪽만 있었으면 HIGH 로 남았을 것이다.

3. 축이 남긴 「확인 불가」를 오케스트레이터가 닫을 수 있다. 축⑥은 SEC-02 의 승격 조건을 열어 뒀는데(훅만 stdin 구동 가능), 오케스트레이터는 실제 Write 도구를 쓸 수 있어 한 번의 측정으로 BLOCKER↔MED 를 갈랐다. 「확인 불가」 절은 버리는 칸이 아니라 다음 사람에게 넘기는 작업 목록이다.

4. HIGH↔BLOCKER 불일치는 축 간에 실제로 일어난다. 같은 결함을 축⑩은 HIGH(SHIP-03), 축⑪은 BLOCKER(OPS-02)로 봤다. 규칙대로 상향 채택했다 — 심각도는 올릴 수만 있다.

5. 병렬 에이전트에게 「샌드박스에서만」은 지시로 부족했다. 한 에이전트가 대상 저장소를 오염시켰고 그 여파가 나머지 감사 전체에 남았다. 다음 감사에서는 대상 저장소의 읽기 전용 사본을 만들어 그 경로만 주는 것이 옳다.

6. 부하 창이 항상 나쁜 것은 아니다. 결정성(G11)은 load 14→36 의 악조건에서 3/3 동일이 나와, 조용한 창보다 강한 근거가 됐다. 타이밍 게이트(G7)만 조용한 창을 요구한다 — 무엇을 재느냐로 갈린다.

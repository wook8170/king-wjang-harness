## 1. 이음매 점검 — 축끼리 어긋난 곳

### 🔴 이음매 A — 「과차단 0」과 「과차단 25%」가 같은 대장에 있다 (해소됨: 모순 아님)

| 출처 | 주장 |
|---|---|
| 축④ USE-06 | **과차단 0/20** — 정당한 설계 트랙 작업 20종 전부 allow |
| 축⑥ SEC-13 | **과차단 0/14** — 정당한 조회·백업·개발 명령 전건 allow |
| 축② API-01 · 오케스트레이터 ORCH-09 | **과차단 8/32 ≈ 25%** |

**읽는 사람이 반드시 걸려 넘어질 자리다.** 대장만 보면 같은 제품에 대해 정반대 수치가 있다.

**해소 — 셋 다 맞다. 서로 다른 것을 쟀다.**

- 축④의 20종은 **쓰기** 명령이다(문서·테스트·설정·자산 파일 생성). 전부 단순 형태였다.
- 축⑥의 14종은 **읽기·백업** 명령이되 **리다이렉트가 없거나 `2>/dev/null` 같은 진짜 파일
  리다이렉트**였다. `cat $D/config.yaml` 같은 변수 경로도 포함돼 있었으나 통과했다.
- 축②와 오케스트레이터가 잡은 8건은 **네 가지 특정 구문**에서만 나온다:
  `N>&M`(FD 복제) · 따옴표 닫힌 heredoc **본문** · `cd X &&` 접두사 · 명령 텍스트 어디든의 승인 문구.

즉 **과차단은 명령의 *의미*가 아니라 *구문 형태*에 걸린다.** 앞선 두 축의 배터리에 그 네 형태가
없었을 뿐이다. 세 결과를 합치면 실제 그림은 이렇다:

> **의미상 정당한 명령은 대부분 통과한다. 그러나 특정 구문 네 가지가 섞이면 의미와 무관하게
> 거부되고, 그 네 가지는 셸에서 매우 흔하다.**

이 해소를 대장에 남기지 않으면 다음 세션이 「축④가 틀렸다」거나 「API-01 이 과장됐다」로 읽는다.
**둘 다 아니다.**

### 이음매 B — 같은 결함에 축마다 다른 심각도 (상향 채택)

| 결함 | 축⑩ | 축⑪ | 채택 |
|---|---|---|---|
| `core/dist` 부재 시 훅 침묵 | SHIP-03 **HIGH** | OPS-02 **BLOCKER** | **BLOCKER** |

규칙대로 **올리는 쪽을 택했다**(심각도는 올릴 수만 있다). 두 축이 같은 현상을 보고 다르게 매긴
이유는 렌즈 차이다 — 축⑩은 「배포 전제가 누락됐을 때의 동작」으로 봤고(계약대로 exit 0 이니 HIGH),
축⑪은 「강제가 꺼진 것을 알 수 있는가」로 봤다(알 방법이 0이니 BLOCKER). **축⑪의 렌즈가 이
제품의 판매 명제에 더 가깝다.**

### 이음매 C — 같은 결함이 두 축에 두 ID 로 (교차 표기)

| 사안 | ID | 처리 |
|---|---|---|
| `core/test/` 가 배포본에 실린다 | DEP-04(축⑦) · SHIP-11(축⑩) | 둘 다 남기되 서로 교차 표기 — 한쪽은 공급망 표면, 한쪽은 배포 산출물 관점 |
| `2>&1` 과차단 | API-01(축②) · ORCH-05(오케스트레이터) | **API-01 을 정본 BLOCKER 로**, ORCH-05 는 독립 재발견(교차 확증)으로 표기. **차단 결함 수는 3 — 4가 아니다** |
| dist↔소스 파리티 | SEC-06 · SHIP-16 · API-23 · DET-03 | 넷 다 남긴다 — **독립 4회 확인**은 그 자체가 강한 근거다 |

### 이음매 D — 「표시 = 강제」 대조

축⑧이 명시적으로 본 항목이다. `--help`·문서가 말하는 허용 경로와 `policy.ts` 가 실제 판정하는
허용 경로는 **일치했다**(축④ USE-06 의 경계 케이스 BD01~04 가 README 약속 「Anything under
`.harness/`, `docs/` … always writable」을 그대로 지킨다). **표시와 강제가 갈리는 사례는 못 찾았다.**

다만 반대 방향의 갈림이 하나 있다: **README 는 강제를 광고하는데 특정 상태에서 강제가 꺼진다**
(OPS-02). 이건 표시↔강제 불일치라기보다 **광고↔실물 불일치**이고, 이미 BLOCKER 로 잡혀 있다.

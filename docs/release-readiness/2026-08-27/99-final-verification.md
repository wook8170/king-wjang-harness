  리다이렉트**였다. `cat $D/config.yaml` 같은 변수 경로도 포함돼 있었으나 통과했다.
- 축②와 오케스트레이터가 잡은 8건은 **네 가지 특정 구문**에서만 나온다:

즉 **과차단은 명령의 *의미*가 아니라 *구문 형태*에 걸린다.** 앞선 두 축의 배터리에 그 네 형태가
없었을 뿐이다. 세 결과를 합치면 실제 그림은 이렇다:

> **의미상 정당한 명령은 대부분 통과한다. 그러나 특정 구문 네 가지가 섞이면 의미와 무관하게
> 거부되고, 그 네 가지는 셸에서 매우 흔하다.**

이 해소를 대장에 남기지 않으면 다음 세션이 「축④가 틀렸다」거나 「API-01 이 과장됐다」로 읽는다.

## 6. 게이트 × open 기계 대조 (2026-08-28 신설)

**왜 신설했나.** §1 의 이음매 점검은 「**축끼리** 어긋났는가」만 봤다. 47차에서 드러난 두 사고는
둘 다 「**축의 결론이 게이트 판정과** 어긋났는가」였다 — 그 각도가 절차에 없었다. 그래서
**게이트별로 「이 게이트의 목표를 깨는 open 항목이 있는가」를 전수 대조**하는 단계를 넣는다.

방법: `awk` 로 대장에서 `open` 행 전수를 뽑고(집계와 목록이 갈리지 않게 기계로), 각 행을 13개
게이트의 **착수 전 확정 목표 문장**에 하나씩 대본다. 판정을 낮추는 것이 아니라, **목표 문장이
무엇을 포함하고 무엇을 포함하지 않는지**를 명시하는 것이 이 절의 산출물이다.

### 6.1 게이트를 실제로 깬 항목 — 3건, 전부 이번에 닫았다

| 게이트 | 깬 항목 | 왜 깨는가 | 처리 |
|---|---|---|---|
| **G3** 광고↔실물 불일치 0 | **SHIP-02** | README 명령표가 `harness …` 로 쓰였는데 사용자 셸에는 그 이름이 없다 | README 4언어에 「`harness` 는 어디 있나」 문단 추가 — 에이전트 셸/사용자 셸 구분을 적고, 청정 env 로 **실측한** PATH 한 줄을 준다 |
| **G3** | **SHIP-04 의 문서 부분** | `README:114` 「Self-contained … `npm audit --omit=dev`: 0 vulnerabilities」가 **설치 경로에 대해서는 거짓 인상**을 준다 — 그 경로에서는 73패키지·66MB 가 내려온다 | 4언어 문안을 「**런타임** 자체완결」로 정정하고, 캐시에 내려오는 것과 **실행 경로에 없다는 것**을 같은 불릿에 적었다. 69MB 왕복·잔여라는 «비용» 자체는 SHIP-04 로 계속 open |

목표를 사후에 좁히는 것이 아니라, 착수 전 문장이 원래 무엇을 재기로 했는지를 적는다.

| **G1** 테스트 fail 0 · **G7** 대용량 무한대기 0 | ~~PERF-08~~ **기각** → **PERF-09(LOW·open)** | **50차에 여기만 판단을 미뤘고, 51차에 실측으로 풀었다.** 50차: 회귀 테스트가 단독 반복 8회 중 3회 실패하고 같은 입력에서 12.5s(예산 10s)를 관측해 두 목표 문장을 실제로 스쳤다 — 다만 **측정 창이 오염돼**(세션 내내 load 6→88, 타 세션 vitest 2건) 유휴 판정이 불가능했다(50분 감시에도 창이 안 열렸다). 51차: 유휴 창이 열렸고(**load1m 3.82**) 단독 8회 재측정 결과 `4037/4099/4444/4323/4149/4293/5992/4397 ms` — **8/8 통과 · 알람 8000ms 대비 여유 1.9배**. 50차의 실패는 **제품이 아니라 기계를 잰 것**이었다. 두 칸 모두 **충족 확정**, PERF-08 **기각**(48차 [DEP-11] · 50차 [SEC-17] 과 같은 처리). **남기는 것**: ① 게이트 목표 문장은 보류 중에도 손대지 않았다 — 낮춘 것은 판정이지 기준이 아니다 ② 소동이 드러낸 진짜 결함은 **[PERF-09]** 다(회귀 테스트에 부하 창 판정 부재 — 「기계가 바쁨」을 「예산 초과」로 보고한다). **부하 민감성은 실재한다**: load 3.9 에서 4037ms 이던 것이 load 5.3~6.0 에서 5992ms 로 올라 여유가 1.33배까지 준다 |
| **G8** 소스 쓰기 관통 0 | ~~SEC-17~~ **기각** | 과차단으로 등재했다가 **기각**했다 — 그 관측은 리포가 아니라 **설치본(웨이브 32)** 을 잰 것이었다. 리포 HEAD 로 맞춘 뒤 재측정하니 전부 ALLOW 다. G8 에 영향 없음. **남는 교훈은 [DEP-03]**: 훅을 통해 본 동작은 설치본의 것이지 리포의 것이 아니다 |

### 6.3 G9 — 근거 문장을 갈아 끼웠다 (판정은 유지, 근거는 교체)

**폐기한 문장** 「devDependency 는 설치자 머신에 안 내려온다」(DEP-11, `code` 추론) — **거짓**.

**새 문장**(전부 `measured`, `evidence/recheck-dep11-ship02.log`):

1. **내려온다.** 문서대로 설치된 실기 HOME 의 플러그인 캐시 **4버전이 전부** `node_modules`
   66MB·73패키지를 갖고 있다(총 609MB). `vitest 2.1.9` · `vite 5.4.21` · `esbuild 0.27.7` —
   `npm audit` 의 critical 1(vitest) · high 1(vite) 근원이 **그대로 실재한다**.
2. **그러나 실행 경로에 없다.** `node_modules` 를 뺀 사본에서 `bin/harness --version`·`status`
   와 `mcp/server.js` 의 `initialize` 핸드셰이크가 **정상 동작**한다. 실행 진입점 4개
   (`core/dist/cli.js` · `core/dist/mcp.js` · `bin/harness` · `mcp/server.js`)의 외부 `require`
   는 **Node 내장뿐**이다.
3. **설치 시점 실행도 없다.** `npm ci` 는 **`--ignore-scripts`** 로 돈다(`ax10-plugin-npmci.log:8`).
4. 두 권고 모두 **개발 서버를 띄워야** 발동한다(vitest UI 서버 / vite dev optimized-deps).
   이 플러그인은 그것을 띄우는 경로가 없다.

→ **「프로덕션 도달 critical/high 0」은 유지된다.** 바뀐 것은 *왜* 도달하지 않는가다:
「안 내려온다」가 아니라 **「내려오지만 실행되지 않는다」**. 디스크 적재라는 «비용»은 게이트가
재는 대상이 아니므로 **SHIP-04(MED, open)** 가 계속 들고 있는다.

### 6.4 대장 위생 — 낡아서 판정과 어긋난 행

- **PERF-03**(open, `claimed`, 「G7 미실시」) — 이후 유휴 창(load 3.95)에서 **실측 완료**되어
  G7 이 충족 판정을 받았다(`g7-bench-idle.log`). 행이 소멸했는데 `open` 으로 남아 **대장이
  게이트와 반대말을 하고 있었다.** `verified` 로 닫았다.

  게이트 표와 대조하는 것이 이 §6 의 일이다.

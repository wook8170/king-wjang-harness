# 03. UI·접근성 — 터미널 출력 품질 · i18n · 비ASCII 안전 (CLI 재해석)

**감사 모델**: Claude Sonnet 5 · **위임 도구**: 직접 수행(에이전트 서브프로세스 실행) · **감사일** 2026-08-27
**대상 커밋** `bacb4bc`

매체: CLI 도구 — `media-adapters.md` 의 CLI 표 적용. 이 축 = 「TTY/비TTY 출력 분기 · NO_COLOR ·
터미널 폭 · 비ASCII 경로/인자」.

## 방법 — 실제로 무엇을 했나

전부 샌드박스에서 실행. 저장소는 읽기 전용(`node <repo>/bin/harness <cmd>` 를 샌드박스 cwd 에서
호출 — `CLAUDE_PROJECT_DIR` 미설정 확인 후 실행하므로 `.harness/`는 샌드박스에만 생긴다).

1. `SANDBOX=.../scratchpad/ax03/한글경로-테스트` 를 만들고 그 안에서 `harness init` ·
   `harness node upsert`(긴 한글+이모지 제목) · `harness report {rtm,hub}` · `harness doctor` ·
   `harness --help` / `node --help` / `tokens --help` 를 실행.
2. `SANDBOX/many-items-test` 에 C-1..C-200 (각 한글 제목 + 이모지) 을 `harness node upsert` 200회
   등록(73초) 후 `node list` · `report rtm` · `doctor` · `trace C-150` 로 규모 테스트.
3. `SANDBOX/lang-test`(`lang: ko`) · `SANDBOX/lang-ja-test`(`lang: ja`, `HARNESS_LANG=ja/zh`) 로
   언어 분기 실측.
4. `SANDBOX/longtext-test` 에서 `bin/harness-hook pre-tool` 에 9000자 파일 경로를 담은 stdin
   JSON 을 흘려 훅 deny 경로를 실측. 한글 경로에 대해서도 동일하게 실측(항목 1).
5. ANSI 이스케이프는 `python3` 로 stdout 바이트열의 `0x1b` 개수를 직접 세어 확인
   (환경의 `grep` 이 `ugrep` 별칭이라 `$'\x1b\['` 패턴이 깨져 `od -c | grep 033` 오탐이 났던 것을
   python 바이트 카운트로 교차검증함 — 결과 0으로 일치).
6. `NO_COLOR=1` / `FORCE_COLOR=1` / `TERM=dumb` 각각으로 `--help` 를 실행해 무색 기준 출력과
   `diff` — 바이트 동일 여부 확인.
7. `COLUMNS=40/80/200` 으로 `--help` 를 실행해 `diff` — 바이트 동일 여부 확인 후, 코드에
   `process.stdout.columns` 참조가 있는지 `grep` 으로 대조. 실제 80열 줄바꿈 모습은
   `fold -w 80 -s` 로 재현.
8. `core/src/i18n.ts` · `core/src/tr.ts` 전문 정독. `core/src/*.ts` 전체에서 `en:`/`ko:` 리터럴
   428/427개를 node 스크립트로 대조(스크립트는 `scratchpad/ax03/check_i18n_pairs.mjs`) —
   불일치 5건은 전부 동일 줄 `en: '...', ko: '...'` 패턴을 스크립트가 놓친 오탐임을 수동 확인.
   보간 자리(`${}`) 개수 대조 스크립트(`check_placeholders.mjs`)도 시도했으나 중첩
   `t({en,ko})` 호출을 다중행 휴리스틱이 잘못 묶어 73건의 대량 오탐이 나왔음을 여러 건 수동
   대조(doctor.ts:264-269, migrate.ts:120-123 등)로 확인 — 실제 불일치 0건.
9. `README.md`·`README.ko.md`·`README.ja.md`·`README.zh.md` 의 `HARNESS_LANG`/`lang` 문서화
   문구와 헤더 구조(`##`/`#` 개수)를 대조.
10. `skills/*/SKILL.md` 15개 + `agents/*.md` 6개의 frontmatter(`name`/`description`/`tools`/
    `model`)를 python/awk 로 추출해 존재·길이 검사.
11. `help.ts` 의 유일한 열-정렬 함수 `table()` 의 모든 호출부(`grep -n "table("`)를 대조해
    실제로 사용자 데이터(한글 제목 등)가 그 함수에 들어가는 경로가 있는지 확인.

## 발견

### [UX-01] MED — 긴 `--help` 행이 80열 터미널에서 열 정렬 없이 줄바꿈된다

**근거등급** measured
**근거**
`core/src/help.ts:219-226` (`table()` — 좌열 폭을 `r.left.length` 로 계산해 `padEnd(width)` 하고,
넘치는 요약문은 오른쪽에 그대로 이어붙임. 연속행에 들여쓰기 재적용 없음)
`core/src/help.ts:43-50` (`doctor` 항목 summary — 영문 178자 한 줄)
`core/src/help.ts:141` (`tokens gen` 항목 summary — 173자)
`core/src/tokens.ts:126` (`TOKEN_DOC_SHAPE_HINT` — `tokens --help` note 에 삽입되는 231자 한 줄)

재현:
```
cd <sandbox>/한글경로-테스트
node <repo>/bin/harness --help | fold -w 80 -s | sed -n '10,13p'
```
출력(실측, 2026-08-27):
```
  doctor          Diagnose state vs journal and policy drift; --repair replays 
state, --accept-policy re-pins the policy baseline (needs 
HARNESS_ACCEPT_POLICY=1 — humans only).
  phase <sub>     Move to a phase. Only an approved gate opens the next phase.
```
`COLUMNS=40/80/200` 세 값으로 `--help` 를 실행해 `diff` 하면 바이트 단위로 완전히 동일함 —
`grep -rn "process.stdout.columns\|COLUMNS" core/src/*.ts` 결과 0건, 즉 앱이 터미널 폭을 전혀
읽지 않고 고정 텍스트만 낸다. 짧은 요약은 문제없이 지나가지만, 173~231자짜리 요약은 실제
80열 터미널에서 두 번째 이후 줄이 원래 들여쓰기(설명 칸 시작 위치)로 돌아가지 않아 `doctor` 항목의
표 구조가 시각적으로 깨진다.

**무엇이 깨지는가** 사람이 실제 80열 터미널(기본값)에서 `harness --help`·`harness tokens --help`
를 읽을 때, `doctor`/`tokens gen`/토큰 문서 힌트 줄이 왼쪽 정렬 없이 다음 줄로 흘러나가 어느
명령의 설명인지 시각적으로 추적하기 어려워진다. 기능은 깨지지 않는다(파싱 대상은 에이전트가
아니라 사람이며, 텍스트 자체는 손상되지 않는다) — 그래서 BLOCKER/HIGH 가 아니라 MED.

**제안** `table()` 에서 넘치는 요약문을 폭 기준으로 접어(word-wrap) 계속 행마다
`' '.repeat(width)` 들여쓰기를 반복 적용하거나, 요약문 자체를 100자 내외로 줄인다.

### [UX-02] — (결함 아님·전제 정정) 런타임 i18n 은 en/ko 2언어만 지원한다 — 「4언어」는 README 문서에만 해당

**근거등급** code + measured
**근거**
`core/src/i18n.ts:17` — `export const LANGS = ['en', 'ko'] as const;`
`core/src/config.ts:81-82` — `lang` 해석이 `isLang()` 통과 값(en/ko)만 받고 그 외는
`DEFAULT_CONFIG.lang`(en) 로 떨어짐.
`README.md:223` — `lang` 문서화 문구 자체가 "Set `ko` for Korean, or export `HARNESS_LANG=ko`"
라고만 적고 있어 제품이 ja/zh CLI 출력을 스스로 광고하지 않음(과대광고 아님).
재현(measured):
```
cd <sandbox>/lang-ja-test   # .harness/config.yaml 에 lang: ja 추가
node <repo>/bin/harness --help   # → 영어로 출력(깨지지 않고 안전 폴백)
HARNESS_LANG=zh node <repo>/bin/harness foobar   # → 영어 "Unknown command" 로 폴백
```

**무엇이 깨지는가** 아무것도 깨지지 않는다 — 이것은 감사 브리핑의 전제(「i18n 4언어 en/ko/ja/zh」)가
실제 코드와 다르다는 점을 밝히는 정정 행이다. `README.ja.md`/`README.zh.md`는 실재하고
헤더 구조도 en/ko 와 동일(24/24/24/24, `grep -c '^#'`)하지만, 이것은 **GitHub/마켓플레이스에서
읽는 문서 번역**이지 CLI 런타임 출력 언어가 아니다. `HARNESS_LANG=ja`/`zh` 나 `lang: ja`/`zh` 를
줘도 크래시·undefined 노출 없이 영어로 안전하게 떨어진다(measured) — 이것이 "4언어 키 누락"
판정선이 요구하는 실패 모드라면 **없음**이지만, "CLI 가 4언어를 지원한다"는 전제 자체가 성립하지
않으므로 다음 세션·경영진 보고 시 착오하지 않도록 여기 명시해 둔다.

**제안** (선택) README 의 언어 스위처(`한국어 | 日本語 | 中文`)와 `lang:` 설정 표 사이에 "문서
번역 4개 언어 vs CLI 출력 언어 2개(en/ko)"를 한 줄로 구분해주면 다음 세션·사용자 혼동을 막는다.
지금 상태도 과대광고는 아니므로 BLOCKER/HIGH 아님.

## 확인 불가

- **Claude Code 플랫폼이 강제하는 `name`/`description` 의 정확한 상한 글자수**는 이 세션에서
  공식 스펙 문서를 열어보지 못해 코드로 확정하지 못했다(가장 긴 값 577자가 안전 범위인지는
  현재 관측된 정상 렌더링(UX-13)으로 간접 확인했을 뿐). 플랫폼 스펙 문서나
  `claude plugin eval` 리포트를 받으면 수치로 확정할 수 있다.
- **실제 협소 터미널 폭(iPad SSH 클라이언트 등 40열 이하)에서 사람 눈으로 본 최종 가독성** —
  이 세션은 `fold -w 80 -s` 로 실제 80열 하드랩을 근사 재현했을 뿐, 실물 터미널 에뮬레이터
  화면 캡처는 하지 않았다. 실기기/실제 터미널 앱 스크린샷을 주면 UX-01 의 체감 심각도를
  더 정확히 매길 수 있다.
- **스크린리더(VoiceOver 등) 완주** — CLI 매체 재해석표에 해당 항목이 없어(GUI 접근성 항목은
  네이티브 데스크톱 앱 표에만 있음) 대상에서 제외했다. 필요하면 별도로 범위를 정해 재감사.

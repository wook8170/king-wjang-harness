## 왜 미뤘나 — 측정 위생

`measurement-hygiene.md` 의 첫 문장이 이 축의 이유다: **「오염된 창에서 잰 수치는 틀린 수치보다
나쁘다. 틀린 수치는 의심받지만 오염된 수치는 초록색으로 보인다.」**

측정 시도 시점(2026-08-28 00:23)의 창 상태:

```
$ uptime
0:23  up 5 days, 4:37, 1 user, load averages: 17.17 20.26 21.60      # 10코어

$ ps -Ao pid,pcpu,etime,comm | sort -k2 -rn | head -3
27857 357.6  10:31:57  OrbStack Helper                                 # ← 폭주
  171  40.4  05-04:32:42  WindowServer
 6315  19.1     44:35  bfs
```

`OrbStack Helper` 가 **357% CPU 를 10시간 반째** 먹고 있었다. 이것은 감사 에이전트가 만든 부하가
아니라 **사전에 존재하던 폭주 프로세스**이고, `measurement-hygiene.md` 가 실측 사례로 적어 둔
상황(「부모가 죽어 고아가 된 빌드 프로세스가 250% CPU 를 3시간째, 15분 로드 평균 12.45」)과
같은 부류다. 그 창의 수치는 전부 버려야 한다.

**부하에 둔감한 게이트는 그대로 진행했다** — G1(테스트 pass/fail)·G2(tsc)·G11(결정성).
결과는 `09-determinism.md`. 부하는 pass/fail 을 바꾸지 않고, 오히려 결정성 판정을 강화했다.

| 항목 | 목표 | 상태 |

| 폴백이 **추가**하는 훅 지연 (wall-clock) | **< 50 ms** | 미실시 |

50 ms 는 제품 README 가 **스스로 선언한 문턱**이고, 10 ms 는 README 의 `~4 ms p95` 주장에 2.5배
여유를 준 값이다. **이 목표는 착수 전에 확정했고 그대로 둔다** — 잴 수 없다고 낮추지 않는다.

## 다른 축이 정성적으로 확인한 것 (이 축의 대체물이 아니다)

### [PERF-01] — 대용량 저널에서 **체감 정지 없음** (정성 관측, 정밀 수치 아님)
**근거등급** measured (단, 오염 가능성 있는 창) · **근거** `evidence/ax04-BIG.log:4`~`:16`

축④(E2E)가 저널을 **120,027줄 / 15 MB** 로 만들고 정상경로·열화경로를 각각 구동했다:

| 경로 | 호출당 |
|---|---|
| 열화경로(매 훅 12만 줄 재생) | ~471 ms |
| 정상경로 | ~538 ms |
| bare `node -e 0` (부팅 플로어) | 408 ms |
| 비하네스 sh 게이트 | 79 ms |

**저널 크기가 wall-clock 을 늘리지 않았다** — 절대값은 node 부트 플로어가 지배하며, 그것은 이
환경(`/Volumes` 마운트)의 속성이지 제품 결함이 아니다. `axes.md` ⑤의 최대 관심사인 **「한 요청이
전체를 멈추는가」에 대해 「아니오」**를 얻었다.

**그러나 이것은 G7 을 충족하지 못한다.** G7 은 「폴백이 **추가**하는 지연」을 50 ms 문턱으로 묻는데,
위 수치는 델타가 **음수로 나올 만큼 노이즈가 크다**(471 < 538). 노이즈가 신호를 덮은 측정이다.

### [PERF-02] — 반대 방향의 실측: 훅이 10초 예산을 **넘긴다**
**근거등급** measured · **근거** `02-backend.md:164` (축② API-04) · `11-ops.md:83` (축⑪ OPS-06)

두 축이 독립적으로 **훅 타임아웃 초과**를 실측했다:

- 축②: **1.03 MB Bash 명령**에서 PreToolUse 가 **10.1 / 12.8 / 10.5 초** (3회 전부 `hooks.json` 의
  10초 예산 초과). 타임아웃 시 stdout 0바이트 = **무판정 = allow**.
- 축⑪: **거대 저널 + 손상된 상태 파일** 조합에서 10초 초과 — README 의 「bounded」 주장이 실측
  규모에서 깨진다.

**이 축이 제대로 측정되면 이 두 결과와 이어 붙여야 한다.** G7 의 「추가 지연 < 50 ms」는 정상
경로의 질문이고, 위 둘은 **꼬리(tail)의 질문**이다. 꼬리에서 이미 예산을 넘겼다는 실측이 있는
이상, 이 축의 재측정은 **평균이 아니라 p99 와 최악 입력**을 봐야 한다.

## 확인 불가

- **G7 전 항목** — 조용한 창이 필요하다. 사용자가 폭주 프로세스를 종료하고 저장소 루트의 활성화를
  제거하면(둘 다 사람만 할 수 있다) 위 「재는 방법」 3줄로 바로 판정할 수 있다.
- **1000 노드 규모 원장 조회 지연** — 축⑧이 시도했으나 감사 중 오염된 훅이 시딩 스크립트를 반복
  거부해 실패했다. 코드상 `loadLedger` 전량 파싱 + `upsertNode` O(n) 재기록(순차 1000회 = O(n²),
  유계)으로 판단되나 **실측치 없음.**
- **동시 사용자·동시 세션 부하** — 이 매체에서는 「한 머신에서 여러 Claude Code 세션이 같은
  저장소에 훅을 건다」에 해당한다. 축④이 40 프로세스 동시 append 안전성은 확인했으나(USE-11),
  **지연 관점의 동시성 측정은 하지 않았다.**

# 09. 결정성 · 재현성

**감사 모델**: 오케스트레이터(Opus 5, 메인 세션) 직접 중앙 실행 · **위임 도구**: vitest 2.x · **감사일** 2026-08-28
**대상 커밋** `bacb4bc`

> **왜 중앙 실행인가.** 축 감사 에이전트 9명 전원에게 `npm test` 전체 실행을 **금지**했다.
> 9개가 동시에 vitest 를 돌리면 서로를 플레이키로 만들고, 그 결과가 이 축의 판정을 통째로
> 오염시킨다(`measurement-hygiene.md` 「다중 에이전트가 공유 자원」). 그래서 이 축만 에이전트가
> 전부 끝난 뒤 오케스트레이터가 한 창에서 잰다.

## 방법 — 실제로 무엇을 했나

```
uptime; ps -Ao pid,pcpu,etime,comm | sort -k2 -rn | head -5; df -h /   # 창 위생 기록
npm run check                                                          # G2
shasum -a 256 core/dist/cli.js core/dist/mcp.js                        # 산출물 해시 고정
for i in 1 2 3; do npm test; done                                      # G1 · G11
```

전체 출력: `evidence/g1-g11-vitest-x3.log`(41줄).

## 창 위생 — 이 창은 **조용하지 않았다**

| 실행 | 시각 | load(1분) |
|---|---|---|
| RUN 1 | 00:23:50 | **14.38** |
| RUN 2 | 00:24:18 | **27.42** |
| RUN 3 | 00:24:41 | **35.59** |

10코어 머신에서 load 14~36 이다. `OrbStack Helper` 가 357% CPU 를 10시간째 점유 중이었다.

**이 사실을 숨기지 않고 적는 이유**: 부하는 **타이밍 수치를 무효로 만들지만, pass/fail 결정성
판정은 오히려 강화한다.** 조용한 창에서 3/3 통과하는 것보다 **부하가 3배로 오르내리는 창에서
3/3 이 동일한 것**이 결정성의 더 강한 증거다. 반대로 이 창의 `Duration` 수치(22~25초)는
**타이밍 근거로 쓰지 않는다** — 그건 축⑤ 소관이고 조용한 창을 기다린다.

부수 게이트 G1(테스트 fail 0)·G2(tsc 0)도 이 실행으로 함께 충족됐다.

## 확인했고 괜찮았던 것 (verified/measured 행)

### [DET-01] — 악조건 3회 반복에서 결과 완전 동일
**근거** `evidence/g1-g11-vitest-x3.log:2`·`:6`·`:10` — 세 실행 모두 58 파일 / 1404 테스트 전건 통과.
load 가 14.4 → 27.4 → 35.6 으로 2.5배 변동하는 동안 **결과가 한 건도 흔들리지 않았다.**

### [DET-02] — 이전 세션이 고친 부하 민감 단언이 실제로 버텼다
**근거** 선행 핸드오프(38차)가 `FLAKE-01` 로 절대 wall-clock 단언 2건을 **부하 둔감형**으로 바꿨다
(비율 기반 · 최소값 3회 + 부류 문턱). 이번 실행은 그 수정이 **의도한 조건에서 검증된 첫 사례**다 —
load 35.6 은 원 재현 조건(load 158)보다는 약하지만, 수정 전 회귀가 실패하던 영역(load 12 대)을
**세 배 이상 넘긴 창에서 3/3 통과**했다. 「고쳤다」가 「재측정했다」로 바뀐 지점.

### [DET-03] — 재현 가능 빌드가 세 경로에서 독립 확인됐다
**근거** 축⑥(`evidence/ax06-dist-parity.log`) · 축⑩(`10-deploy.md:431`) · 축②(`02-backend.md:613`)가
서로 모른 채 각자 `tsup` 재빌드 후 커밋된 `core/dist/{cli,mcp}.js` 와 대조해 **전부 바이트 일치**를
얻었다. 커밋된 산출물이 소스에서 재현된다 — **소스 리뷰가 실제 실행 코드를 검증한다**는 뜻이고,
공급망 관점에서도 중요한 성질이다(축⑦ DEP-07 과 교차).

### [DET-04] — 감사 자체가 워킹트리를 오염시켰음에도 테스트가 흔들리지 않았다
**근거** 이 실행 시점에 저장소 루트에는 감사 중 잘못 생성된 활성화 디렉터리가 남아 있었다
(`00-summary.md` 「측정 위생」). 즉 저장소가 자기 훅의 통치를 받는 비정상 상태였는데도
**1404 전건이 통과**했다 — 테스트 스위트가 저장소의 활성화 상태에 의존하지 않는다는 부수 확인이다.
(다만 이 상태는 제거돼야 하며, ⑤ 타이밍 재측정은 제거 후로 미룬다.)

## 확인 불가

- **마이그레이션 양방향** — `axes.md` ⑨의 「빈 DB → 최신 / 구 버전 데이터 → 최신 / 롤백
  마이그레이션」은 이 매체에서 `.harness/` 스키마 마이그레이션에 해당하며, **축⑩이 실측했다**
  (SHIP-14 업그레이드 2건 데이터 손실 0 · SHIP-15 롤백 리허설 · SHIP-22 미지 이벤트 거부).
  이 축에서 중복 측정하지 않았다 — 같은 모달리티를 쌓으면 사각도 같이 움직인다.
- **테스트 순서 무작위화** — vitest 기본 순서로만 3회 돌렸다. `--sequence.shuffle` 로 순서를 섞은
  반복은 하지 않았다. 조용한 창이 확보되면 순서 무작위화 3회를 추가하는 것이 이 축의 다음 작업이다.
- **더 강한 부하에서의 재현** — load 158 수준(FLAKE-01 원 재현 조건)은 이번에 만들지 못했다.

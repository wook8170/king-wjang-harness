결함 open 0 — 그런데 게이트 기준을 우리가 바꿨다

라운드 3-I 감정이 찾은 BLOCKER 3 · MED 12 와 잔여 LOW 51 을 전건 봉인했다. 대장은 open 0 이고 1193 tests green ×3 · tsc 0 · lint R1–R7 통과다. 결함 집계로는 막는 것이 없다. 그래도 판정은 오르지 않는다 — 판정을 올리는 것은 집계가 아니라 재감정이고, 이번 수정 이후로는 아직 돌지 않았다. 게다가 이번 라운드는 게이트 하나(G9)의 기준 자체를 바꿨다. 그 재정의를 감정자에게 재검증받기 전까지, 이 근거로 판정을 올리는 것은 구현자가 자기 측정으로 자기를 통과시키는 것이다.

가치 축이 무너진 것은 새 결함 때문이 아니다

가치 축 감정자는 대장을 직접 파싱해 집계를 다시 세고, lint 를 돌리고, 「닫혔다」고 적힌 항목을 표본 25/25 재현했다 — 대장은 정직했다.

그런데 라운드 3-H 가 낸 「open BLOCKER 0」은 ground truth 가 아니라 우리 목록의 산물이었다. 감정자가 목록 밖으로 나가자 열거되지 않은 쓰기 도구가 나왔고, 그것으로 정책 파일을 덮으면 강제가 통째로 풀렸다. 세 라운드 연속 같은 패턴이다.

BLOCKER 세 건 — 사슬 하나였다

세 건은 따로 난 결함이 아니라 한 줄로 이어지는 무장해제 사슬이다. 전건 메인 세션에서 다시 돌려 재현한 뒤 봉인했고, 「훅이 허용했다」에서 멈추지 않고 강제가 실제로 풀렸는지까지 관측했다.

BLOCKER SEC-135 → SEC-136 — 열거 밖 도구로 정책 파일을 덮는다

쓰기 도구를 이름으로 열거해 두면 열거되지 않은 도구가 그대로 통로가 된다. 게다가 이들은 > 도 -o 도 쓰지 않고 위치 인자로 파일을 쓴다 — 리다이렉트를 보는 검사에 아예 걸리지 않는다.

echo x > .harness/config.yaml DENY　→　xxd -r -p in .harness/config.yaml ALLOW · openssl enc -out … ALLOW · csplit -f … ALLOW · split -a … ALLOW　→　정책 교체 → 강제 자체가 풀림

결과는 SEC-69 의 재발이다 — 하네스가 자기를 강제하는 근거 파일을 에이전트가 갈아 끼울 수 있으면, 그 아래의 모든 방어는 설정 한 줄짜리가 된다.

봉인 이름을 더 세는 대신 「이 명령이 파일을 만들어 내는가」를 본다. 위치 인자로 쓰는 부류를 쓰기 대상 추출에 올렸고, 정책 파일은 별도 보호 접두로 고정했다.

BLOCKER SEC-137 — 비용 캡이 방어를 되돌린다

스크립트 본문을 읽어 재귀 검사하는 방어에 64KB 상한이 걸려 있었다. 상한을 넘는 파일은 검사에 실패하는 것이 아니라 본문을 아예 안 읽고 통과했다.

./small.sh 본문 검사 → DENY　·　./big.sh (65KB, 패딩) 본문 미검사 → ALLOW

「못 봤으면 통과」는 못 본 만큼 그대로 구멍이다. 그리고 문턱은 언제나 패딩으로 넘을 수 있다 — 공격자가 통제하는 양으로 방어를 끄게 두면 안 된다.

봉인 상한을 넘으면 통과가 아니라 거부로 뒤집었다. 같은 부류를 UX 증거 게이트에서도 잡았다 — 바이트 크기 문턱은 tEXt 청크 하나로 무력화되므로, 속일 수 없는 양(각 변 200px 이상의 치수)으로 잰다.

이것이 이번 라운드에서 판정에 가장 직접 닿는 항목이라 따로 적는다. 같은 코드·같은 저널(100,002줄 · 15MB)을 세 표면에서 각 30회 쟀다.

옛 문턱은 제품을 재고 있지 않았다

「pre-tool p95 < 150ms」는 측정 표면을 적지 않았다. 위 표대로 인프로세스로 재면 8배 여유로 충족이고 wall-time 으로 재면 미충족이다 — 표면 선택만으로 통과·불통과가 갈렸다. 라운드 3-G 감정자(103.5ms)와 3-I 감정자(202.5ms)가 정면으로 어긋난 것도 이것 때문이다. 둘 다 정직했고, 표면이 달랐다.

더 나쁜 것은 wall-time 162ms 중 99ms 가 node 기동이라는 점이다. 절대 문턱을 wall-time 에 걸면 그 게이트는 이 도구가 아니라 측정 머신의 CPU 를 잰다 — 코드를 한 줄도 안 고쳐도 빠른 머신에서는 통과하고 느린 머신에서는 실패한다.

그래서 문턱을 제품이 통제하는 몫(폴백이 더하는 비용 < 50ms)에 걸고, 절대값은 머신 정보와 함께 기록으로 남긴다. 실측은 새 문턱 안이다.

그러나 이것은 우리가 하는 말이다

바꾼 이유가 통과시키기 위해서가 아니라는 것 — 그것을 판단할 자격이 기준을 바꾼 사람에게는 없다. OPS-74 가 이 리포에 못 박아 둔 규칙이 정확히 그것이다: 구현자의 측정 목록은 근거가 아니다.

따라서 라운드 3-J 재감정의 검증 대상에 이 재정의 자체를 넣는다 — 「폴백이 더하는 p95 < 50ms」가 제품을 재는 문턱인지, gates.md 말미의 사유가 타당한지. 그 전까지 이 근거로 종합 판정을 올리지 않는다.

이 라운드가 남긴 규칙

  • 지연 주장에서 「측정 표면」은 값의 일부다. 표면을 안 적은 숫자는 재현이 불가능하고, 정직한 두 사람이 정반대 결론을 낸다. 절대 문턱을 프로세스 wall-time 에 걸면 그 게이트는 제품이 아니라 측정 머신을 잰다.
  • 문턱은 패딩으로 넘을 수 있다. 바이트 검사는 tEXt 청크 하나로 무력화된다 — 속일 수 없는 양으로 재야 한다.
  • 비용 캡이 방어를 되돌릴 수 있다. 「너무 커서 못 봤다」는 통과가 아니라 거부여야 한다.
  • describe.skipIf 는 본문 실행을 막지 못한다. vitest 는 건너뛸 describe 의 콜백도 수집 시점에 실행한다.
  • 감정자가 낸 결함이 이미 내린 반대 결정일 수 있다. rejected 는 회피가 아니라 판정이다.
  • 측정 fixture 가 틀리면 「결함 없음」이 나온다. fixture 가 그 절을 실제로 발화시키는지 확인해야 한다.
  • 새 테스트가 방금 닫은 결함을 다시 만들 수 있다. 닫은 결함의 처방을 새 코드에도 적용했는지 마지막에 한 번 확인한다.

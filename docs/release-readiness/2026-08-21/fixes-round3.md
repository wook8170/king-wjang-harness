## [SPEC-60] HIGH — 스펙 §12 「init 시 경고 고지」 미구현

스펙 §12(알려진 한계)는 이렇게 적혀 있다:

> 권한 다이얼로그 승인 장치는 Claude Code의 permission 프롬프트에 의존 —
> 사용자가 해당 명령을 allowlist에 넣어버리면 무력화된다 **(init 시 경고 고지)**.

괄호 안이 구현되지 않았다. `harness init` 은 한 줄만 찍고 끝났다.

**왜 중요한가**: 이건 코드로 막을 수 없는 한계다. 사용자가 `harness gate approve` 를
allowlist 에 넣으면 §4-3 「승인의 최종 클릭은 항상 사람」이 통째로 무력화되고, 하네스가 파는
안전 속성 중 가장 큰 것이 조용히 사라진다. 막을 수 없으면 **말하는 것**이 유일한 방어인데
그마저 없었다.

수정: `init` 이 stderr 로 고지한다. stdout 계약(JSON 파싱 가능)을 깨지 않으려 stderr 를 쓴다.
재측정: 수정 전 고지 없음 → 후 고지 출력, `2>/dev/null` 시 stdout 불변(`round3-verify.log` §2).

## [SPEC-61] HIGH — 스펙 §10 token-guard 흡수 미완: 계산만 하고 전달하지 않았다

스펙 §10은 token-guard 를 「완전 흡수」로 적고 티어 행동까지 명시한다
(90=웨이브 축소, 95=매 턴 지시서 갱신 강제, 99=최종 핸드오프+소환).

`usage.ts` 는 티어를 정확히 계산했다. 그런데 **그 지침을 세션에 전달하는 경로가 없었다** —
`guidanceFor` 의 유일한 소비처가 `harness usage` CLI 한 곳이라, 사람이 그 명령을 직접
치지 않으면 아무 일도 일어나지 않았다. 원본 token-guard 는 훅이 자동으로 주입했으므로,
흡수했다고 적어 놓고 기능은 후퇴한 상태였다.

**설계 판단 하나**: 원본은 「티어가 **상승할 때만** 주입」했다(같은 문구 반복은 무시된다).
그 규칙을 SessionStart 에 그대로 쓰면 안 된다 — **새 세션에는 상승 이력이 없다.**
95%에서 세션이 갈리면 새 세션은 자기가 임계 근처인 줄 모른 채 평소처럼 크게 벌인다.
그래서 SessionStart 는 상승이 아니라 **현재 서 있는 티어**를 말한다(§3-6 연속성 불변식과
같은 이유). 티어가 `normal` 이면 아무것도 넣지 않는다(노이즈 금지 규칙은 유지).

재측정(`round3-verify.log` §3): 수정 전 주입 없음 → 후 `INSTRUCTION(2): [harness] usage at 95%…`,
그리고 티어 기록이 없는 새 샌드박스에서는 주입 4줄 중 티어 문구 **0줄**.

## [LOGIC-63] HIGH — 턴 로그 앵커가 언어에 의존 (라운드 2가 만든 회귀)

`hook.ts` 는 지시서에서 턴 로그를 `'## 턴 로그'` **문자열 일치**로 찾았다.
그런데 라운드 2에서 내가 지시서 본문 템플릿을 i18n 해서, 영문 프로젝트의 지시서는
`## Turn log` 로 생성된다. 결과: **영문 프로젝트에서 SessionStart 턴 로그 발췌가 조용히 빈다.**

예외도 경고도 없다. 그냥 `(none)` 이 나온다 — **이어받기가 가장 중요한 순간에 무음 실패**다.
게다가 프로젝트가 도중에 `lang` 을 바꾸면 과거 파일이 통째로 안 읽힌다.

**교훈**: 파일 구조를 잡는 문자열은 **표시 문자열이 아니라 파싱 앵커**다. 표시용으로 번역하면
파서도 함께 번역돼야 하고, 그 둘이 갈리면 조용히 깨진다. 앵커를 두 언어 모두 매칭하는
정규식으로 바꿨다 — 현재 설정이 아니라 **파일에 실제로 적힌 것**을 기준으로 잡는다.

재측정(`round3-verify.log` §4): 수정 전 영문 지시서에서 발췌 **없음(무음)** → 후 **있음**.
회귀 테스트 2건(두 언어 각 1), 수정 전 영문 케이스가 레드로 나는 것을 먼저 확인했다.

## [OPS-64] MED — 「한국어 0」을 사람이 손으로 재는 구조 자체

라운드 2의 과다 주장은 사람 실수가 아니라 **구조의 산물**이다. 측정 범위가 코드에 없으면
새 명령·새 오류 경로가 사정권 밖으로 조용히 빠진다.

`core/test/i18n-en-default.test.ts` 는 번역을 검사하지 않는다. **측정 범위를 코드로 고정한다.**
`help.ts` 레지스트리를 순회하므로 **새 명령이 자동으로 편입**된다. 6개 절:

1. 도움말 전수(명령 + 하위명령) 2. 무인자·오인자 오류 경로 전수 3. 생성 문서 15종
4. **일부러 만든 고장 상태** — state 부재·저널 손상·미지 이벤트·프로파일 불량·없는 대상 12종
5. 디스크에 남는 산출물 트리 6. 번들 프로파일 데이터 파일

**4번이 핵심이다.** 첫 버전에는 없었고, 그래서 **가드가 물지 않았다** — doctor 문자열을
한국어로 오염시켰는데 테스트가 그냥 통과했다. 정상 실행이 오류 경로를 지나지 않으니
그 문자열이 렌더되지 않았던 것이다. **런타임 테스트는 실행한 경로만 잰다** — 이것이 라운드 2
과다 주장과 정확히 같은 뿌리다. 고장 상태 절을 넣은 뒤에야 오염이 레드로 잡혔다
(`round3-verify.log` §6에 오염→레드, 복구→그린 기록).

## [SEC-65] HIGH — noclobber 무시 리다이렉트가 대상 추출을 빠져나간다

재감정 채점을 위해 실효성 조건을 HEAD 에서 다시 재다가 걸렸다. `>` 뒤에 파이프를 붙인
noclobber 무시 형태가 리다이렉트 추출 정규식에 없었다. **한 글자 차이로** 설계 트랙 소스
차단과 코어 파일 보호가 둘 다 풀린다. 정규식에 선택적 파이프를 넣고 회귀 테스트 3건.

## [SEC-66] HIGH — 변형 명령 안전망이 비대칭이었다

`python3 -c "open('x','w')"` 처럼 대상 추출이 실패하는 변형은 `.harness/` 코어 파일에 대해서만
이름 대조 안전망(`mentionsPath`)이 걸려 있었다. **설계 트랙 소스에는 같은 net 이 없어서**
같은 수법이 코어 파일에는 막히고 소스에는 통과했다.

**방어가 대칭이 아니면 뚫리는 쪽이 정본이 된다.** `pathLikeMentions` 를 신설해 명령 원문에
등장한 경로형 토큰을 뽑고, `mutating` 과 AND 로 묶어 `judgeWritePath` 로 보낸다. AND 가 핵심이다 —
그러지 않으면 `cat src/app.ts` 같은 순수 조회까지 막혀 사람이 하네스를 꺼버린다.

재측정(`round3-verify.log` §7): 우회 매트릭스 **31종 전건 기대대로**, 그중 **의도적 허용 5종은
그대로 allow**(과차단 0). 회귀 테스트 8건.

## [SEC-67] HIGH — 받아쓰기·간접 실행이 판정 자체를 비껴간다

SEC-65·66 을 닫고 매트릭스를 통과시킨 뒤, 「**내용을 만들어 쓰는**」 변형을 더 넣어 봤다.
19종 중 **9건이 통과하고 있었다.**

가장 나쁜 것은 `curl -o src/app.ts <url>` 이다. 「참조 구현을 소스로 받아온다」는
설계 트랙에서 막힌 모델이 아주 자연히 가는 길인데, 리다이렉트도 아니고 알려진 쓰기 명령도
아니라 **대상 추출이 아예 일어나지 않았다** — deny 도 allow 도 아닌, 판정 없음이었다.
같은 이유로 `wget -O`, `xargs -I{} cp {} src/app.ts`(한 겹 감싸기), `prettier --write`,
`eslint --fix` 가 통과했다.

**과차단을 피하는 선이 이 수정의 절반이다.** 함께 못 박은 것:
- `curl -O`(대문자, 원격 파일명 사용)는 **인자가 대상이 아니다** — 대상으로 잡으면 URL 이
  경로로 오인된다. 소문자 `-o`/`--output` 만 본다.
- `prettier --check` · 플래그 없는 `eslint` 는 조회이므로 통과한다(`sed -i` 와 같은 규칙).
- `git checkout -- src/x.ts` 는 **의도적으로 허용**한다. 복원이지 구현이 아니고, 막으면
  하네스 도입 전 소스가 있는 프로젝트에서 정상 복구가 불가능해진다.

재측정(`round3-verify.log` §8): 수정 전 9건 통과 → **후 전건 기대대로**, 과차단 6종 그대로 allow.

## 측정 도구 정정 (방법론)

이 라운드에서 **shell 기반 측정이 두 번 틀렸다.**

1. `grep -c '[가-힣]'` 이 **순수 영문 줄을 한국어로 셌다**(`migrate` 8줄 보고 → Python `re` 로 0줄).
2. 우회 매트릭스 프로브에서 shell 인용이 **파이프 문자를 먹어** `>` + 파이프 형태를 잘못
   allow 로 보고했다(실제로는 그때도 일부 deny). 파일 기반 Python 프로브로 다시 짰다.

이후 수치는 전부 Python 기준이다. **측정 도구가 틀리면 결론이 아니라 방향까지 뒤집힌다** —
이 라운드의 두 신규 결함(SEC-65·66)은 다행히 재측정으로 살아남았지만, 반대 방향(있는 결함을
없다고 보고)이었으면 그대로 묻혔다.

라운드 2 증거 로그는 grep 기반이지만 **전부 「0」 보고였다.** 오탐은 과대계상 방향이라
0을 만들어내지 못하므로 그 결론 자체는 유효하다 — 다만 **범위가 좁았던 것**이 문제였고,
그건 이 라운드가 닫았다.

## 알려진 한계 (새로 추가)

- **번들 `profiles/` 는 영문 단일이다.** 코드 문자열과 달리 `lang: ko` 로 한국어판이 나오지
  않는다 — 파일을 언어별로 고르는 해석기가 없기 때문이다. 한국어 사용자에게는 이 부분만
  기본값 변경이 아니라 **교체**다.
- **`profiles/*/guidance/`·`rules/` 를 아무것도 읽지 않는다.** 스펙 §9는 「페이즈 스킬 주입용」
  이라고 적었지만 코어·스킬·에이전트 어디에도 로드 경로가 없다. 번역은 했으나 **배선은 없다** —
  기능 추가라 이 라운드 범위 밖으로 두고 여기 남긴다.

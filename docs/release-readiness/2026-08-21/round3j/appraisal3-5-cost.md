## G9 재정의 검증 (재현 · 제품을 재는가 · 반론 · 회귀 탐지력)

**대상 저널**: 100,000줄 · 15.8MB · 턴로그 90%+상태전이 10%(구현자가 상정한 「현실 분포」). 열화 = `.harness/state.json` 삭제(저널 재생 폴백 강제). 페이로드 `pre-tool {Bash: ls}`. 클린 구간(load ≈3.0).

### 1. 재현 — **재현된다** (델타 일치, 절대값은 머신차로 어긋남 — 이것이 요점)
| 표면 | 정상 p95 | 열화 p95 | **폴백이 더하는 델타** | 구현자 |
|---|---|---|---|---|
| wall-time | 64.7ms | 97.4ms | **+32.7ms**(p95) / +27ms(p50) | +29 / +32 |
| 인프로세스 | 0.40ms | 21.8ms | **+21.4ms**(p95) / +16.8ms(p50) | +16.3 / +12.5 |

- **wall 델타 +33ms 는 구현자 +29ms 와 4ms 내 일치**. 인프로세스 델타는 내가 +21.4 로 그들 +16.3 보다 ~5ms 높으나 **동일 오더이고 둘 다 50ms 문턱의 절반 이하**. 재현 성공.
- **절대값은 정반대로 어긋난다(정상적, 예상된 일)**: 내 wall 정상 64.7ms vs 구현자 127ms. 원인은 **오직 node 기동차**(내 40ms vs 그들 99ms). 제품이 통제하는 몫(정상 wall − node기동 = 내 64.7−40=~25ms, 그들 127−99=~28ms)은 **머신을 넘어 ~25~28ms 로 안정**. 이 대비가 G9 재정의를 **직접 실측으로 정당화**한다.

### 2. 문턱이 제품을 재는가 — **잰다. gates.md 사유를 직접 재서 확인함**
- gates.md 는 「wall 절대값의 99ms 가 node 기동」이라 절대 문턱은 제품이 아니라 머신 CPU 를 잰다고 주장한다. **나는 node 기동을 직접 쟀다: 39.7ms**(그들 99ms). 같은 코드가 옛 절대문턱 「폴백 p95 < 150」에서 내 머신은 97.4ms **통과**, 구현자 머신은 162ms **불통과** — 코드 한 줄 안 고치고 머신만 바꿔 판정이 갈린다. **재정의는 통과시키려 문턱을 옮긴 것이 아니라, 옛 문턱이 머신을 재던 것을 제품(델타)로 옮긴 정당한 수정**이다. [OPS-74] 재검증 요구를 이 절이 충족한다.

### 3. 반론 검토 — **반론에 실체가 있다(손상 저널 경로를 통해)**
- 사용자가 겪는 것은 wall-time 이 맞다. 델타만 재면 절대 체감 상한이 사라진다. 내 정상 저널에서는 열화 wall 이 97ms 라 문제없어 보인다. **그러나 §최악입력에서 손상 저널의 열화 wall 은 315ms** — 델타 게이트도 옛 150ms 절대 게이트도 **둘 다 못 잡는다**(G9 은 현실 분포만 재므로). 즉 「절대값은 머신 property 라 버린다」는 논리는 **정상 저널에서만 성립**하고, 제품 자신의 코드 경로(손상 파싱)가 만드는 절대 비용에는 방어가 없다.
- **대안**: (a) G9 을 현실 분포 **한 저널이 아니라 저널 부류 집합**(현실·전상태전이·N% 손상)으로 재고 각각 델타 상한을 두기; (b) 머신 정규화 절대 문턱(`값/node기동바닥` 비율); (c) 회귀 대비 문턱(직전 릴리스 델타 대비 +Xms). 지금은 (셋 다 없음.)

### 4. 회귀 탐지력 — **큰 회귀만 잡고 중간 회귀는 샌다**
- 델타의 분산: 정상은 극도로 안정(인프로세스 sd 0.07~0.09ms), 열화 sd 2.09ms(인프로세스)/3.69ms(wall). 델타 노이즈 ≈ 열화 노이즈 ≈ 2ms(인프로세스)/3.7ms(wall). +21ms 델타는 0 대비 ~10σ — **「폴백이 비용을 더한다」는 사실 자체는 재현성 높게 검출**된다.
- 그러나 **문턱 50ms 는 현실 델타 21ms 대비 29ms 여유** → 트립하려면 **2.3배(+29ms) 회귀**가 필요하다. +15ms(70% 슬로다운) 짜리 회귀는 조용히 통과한다. 게다가 문턱이 **현실 분포 한 입력에 고정**돼, 손상·전상태전이 저널만 느려지는 회귀는 애초에 보이지 않는다. **탐지 하한이 너무 높고 입력 커버리지가 한 점**이다.

## 반대 방향 — 비용 절감이 방어를 빼먹는 곳 (그리고 모범 사례)

### 결함 방향
**① [MEDIUM] 열화 폴백이 손상 저널에서 게이트 문턱의 4~20배 — G9 은 그 입력을 안 잰다.**
폴백(`readJournalForReplay`)은 COST-159 로 「타입 문자열을 먼저 훑고 재생대상만 파싱」해 현실 저널을 3배 빠르게 만든다. 하지만 **손상 줄은 항상 프리필터를 빠져나가 `JSON.parse` 로 내려가 throw 한다** — 그 예외 비용이 줄 수에 비례해 쌓인다. 인프로세스 열화 p95(델타=정상 0.4ms 대비):

| 저널(100k줄) | 인프로세스 열화 p95 | wall 열화 p95 | 50ms 델타 문턱 |
|---|---|---|---|
| 현실 분포(90% 턴로그) | 21.8ms | 97.4ms | ✅ (+21) |
| 100% 상태전이(phase-set) | **65.2ms** | — | ❌ (+65) |
| 50% 손상 | **208.7ms** | — | ❌ (+208) |
| 100% 손상(type 없음) | **420ms** | **315ms** | ❌ (+420) |

폴백은 **바로 이 손상 상태를 살아남으려고 존재**하는데, G9 은 가장 친화적인(프리필터가 다 건너뛰는 턴로그) 저널만 재고 「+16~29ms」라 선언한다. **비용 절감(프리필터)이 최악 입력에서 무력화되고, 측정(G9)이 그 입력을 회피한다** — 지난 라운드 64KB 캡과 동일한 부류(비용 낙관치가 방어/체감을 대변하지 못함)가 **성능 게이트 자체에** 남아 있다. 완화: 에이전트가 저널 쓰기를 못 하므로 적대적 유발은 불가(크래시·트렁케이션으로만 도달), 열화 고지는 뜨고 `doctor --repair` 로 종료됨. 그래서 BLOCKER 아닌 MEDIUM.

**② [LOW~MEDIUM] 깊이 캡은 fail-open(침묵 통과), 형제인 크기 캡은 fail-closed — 비대칭.**
스크립트 체인 스캔(`invokedScriptBodies`)은 비용 상한이 둘이다. **크기 캡(64KB)**은 SEC-B3 로 「못 읽으면 `unread` 로 올려 **deny**」(fail-closed) 로 고쳐졌다 — 실측 70KB 패딩 스크립트@깊이1 = **DENY** ✓. 그러나 **깊이 캡(`depth>=3`)**은 그런 신호 없이 조용히 빈 결과를 반환한다. 실측:
- 악성 저널쓰기 스크립트가 4번째 체인 파일(a→b→c→d)에 있으면 → **ALLOW**(강제 우회).
- 70KB@깊이4 → **ALLOW**(깊이 컷이 statSync 전에 리턴해 `unread` 에도 안 실림).

코드가 「깊이 4 는 열려 있다」고 자인한 **문서화된 한계**지만, **동일한 「캡이 조용히 통과시킨다」버그를 크기에는 fail-closed 로 고치고 깊이에는 안 고친 것**이 요점. 에이전트가 4겹 체인을 짜야 해 작위적이라 LOW~MEDIUM.

### 모범 사례(비용 줄이며 방어 안 뺀 곳) — 함께 기록
- **크기 캡 fail-closed(SEC-B3)**: 못 읽은 스크립트를 통과 대신 deny. 70KB@깊이1 실측 DENY.
- **패치 읽기 캡(1MB) fail-closed**: >1MB 패치·stdin 패치 = null(알 수 없음)→**DENY**. 소·대·stdin 3케이스 전부 DENY 실측. 비용을 상한 두면서 「못 봤으니 통과」를 안 만들었다.
- **ReDoS 제거(COST-A)**: 자기호출 판정을 중첩수량자 정규식→선형 스캔. 접두 래퍼 **80개** 병적 입력도 8.2ms 선형(옛 정규식은 25개 8270ms 지수). 최악입력 상한을 낮추면서 판정 내용 불변. 실측 10/20/25/40/80 래퍼 = 2.1/3.4/2.5/4.0/8.2ms.
- **MCP 무사용 0툴(COST-110)**: sh 게이트 절감을 MCP 옆문으로 되무는 것을 막음. 실측 미하네스 0툴.

## 반대 방향 — 비용 절감이 방어를 빼먹는 곳 (그리고 모범 사례)

### ✗ 열린 구멍 — 루트 밖 스크립트를 **비용/범위 때문에 안 읽고 통과**시킨다 (HIGH)
`invokedScriptBodies`(hook.ts:748)는 실행되는 스크립트가 루트 밖이면 `if (isOutsideRoot(rel)) continue;` 로 **읽지도, 「못 읽었다」고 사실을 올리지도 않고 조용히 넘어간다.** 동일 본문을 인라인·루트내로 두면 DENY 인데 루트 밖에 두면 ALLOW 다 — 실측 대조(P7 빌드 페이즈, 샌드박스):

```
A) sh -c 'echo x >> .harness/events.jsonl'   → DENY
B) sh in.sh        (본문이 저널에 append)      → DENY  (루트내 스크립트는 읽음)
C) sh /tmp/o.sh    (동일 본문, 루트 밖)         → ALLOW (empty verdict)  ← 유일한 차이는 위치
```
전체 체인을 실측으로 확인(모든 링크가 에이전트 도구 호출로 도달 가능):
1. **P7 빌드 페이즈**: `Write /tmp/x.sh`(위조 `gate-approved` 본문) → **ALLOW**(루트 밖 Write 는 설계 트랙만 막고 빌드/출하 트랙은 안 막음).
2. `sh /tmp/x.sh` → **ALLOW** → 저널이 실제로 2줄→3줄로 늘고 `{"type":"gate-approved","data":{"phase":"P10"}}` 안착(실측).
3. `replayState`(events.ts:211)는 위조 `gate-approved` 를 **무조건 승인으로 반영**(위협모델 개정1에 따라 저널 무결성 미검사). `harness doctor --repair`(자기호출·허용)가 그 재생 상태를 state.json 으로 **승격** → 사람 승인 없이 배포 게이트 approved(= SEC-49/92/100 BLOCKER 의 부활 경로).

**이것이 이 축의 정확한 표적이다.** SEC-B3(크기 캡)·SEC-175(깊이 캡)는 「비용 아끼려고 안 본다」를 **「못 봤으니 통과」→「못 봤으니 사실을 올린다」(fail-closed)** 로 고쳤는데, **형제인 루트 밖 스킵에는 같은 처방을 안 했다.** SEC-92 렛저는 루트 밖 스크립트를 **「과차단 0/8」 테스트 케이스**로만 다뤘다 — 즉 「막으면 안 되는 정상 케이스」로 취급했고, **저널로 되쓰는 공격 벡터로는 고려하지 않았다.** 처방은 형제 캡과 동일해야 한다: 루트 밖 실행 스크립트가 있으면 통과가 아니라 「루트 밖이라 못 읽었다」는 사실을 올려 판정으로 보내거나, 최소한 그 명령을 opaqueExec 와 같은 부류로 취급.

### ✓ 모범 사례 — 비용을 줄이면서 방어를 지킨 곳
- **SEC-B3 / SEC-175**: 64KB·깊이3 캡을 남기되(비용 방어) 초과분을 **fail-closed 사실로 올린다**(`unread`·`tooDeep` → DENY). 「비용 절감이 방어를 되돌린 것」을 스스로 고친 정본.
- **COST-177**: 타입 못 찾은 줄은 파싱 생략 → 100% 손상 저널 인프로세스 p95 420ms→11.6ms. **그러면서 그 줄을 corruptLines 로 여전히 센다**(방어 유지). 폴백이 가장 필요한 순간(손상)에 가장 빠르게.
- **COST-159**: `"type":"` 리터럴 indexOf 선필터 후 실패시만 정규식 → 현실 분포 3.2x 이득, 최악 +15% 손해를 **주석 표로 정직 고지**(계약).
- **SEC-B1**: 「쓰는 도구 열거」를 뒤집어 **모르는 명령=쓰기 가능(기본 안전)** + READ_ONLY 화이트리스트. 새 도구가 생겨도 fail-closed.

## G9 게이트 자체에 대한 판정
- **문턱(델타 50ms)·표면(양쪽 계측)·입력집합(3부류) 재정의는 타당**하다. 절대 wall 을 문턱으로 쓰면 코드 불변에도 머신만 바꿔 판정이 뒤집힌다는 것을 3-I/3-J 가 실측으로 증명했고, 내 측정도 재확인한다(부하 중 절대 wall 175ms 는 제품이 아니라 부하를 잰 값). 「제품이 통제하는 몫(델타)에 문턱, 절대는 기록」은 옳다.
- **「기록만」 부류 구분도 타당**: all-state 는 저널이 하네스 명령으로만 늘어 도달이 현실적으로 어렵고, UTIL-203 이 「불가능」이라 안 쓰고 숫자(49.4ms 문턱 코앞)를 적은 것은 정직하다. 이미 결함 등재.
- **동봉 벤치(`bench-hook-latency.mjs`)도 감정 대상**: 재현 가능·워밍업 제외·node 기동 분리·busy-guard(load>코어수×0.5 시 판정 보류)·ENG-201 자동 채점(유휴 초과만 exit 1) — **이 축에서 본 벤치 중 가장 규율 있다.** 부하 중 돌렸을 때 busy 경고가 정확히 발화하고 all-state 를 「recorded only」로 옳게 분류했다.
- **미흡**: G9 은 **정상·열화 훅 지연**만 잰다. 위 「반대 방향」의 방어-비용(스크립트 스킵의 fail-open)은 G9 의 시야 밖이다 — 게이트가 「폴백이 얼마나 느린가」는 묻지만 「비용 캡이 무엇을 통과시키는가」는 묻지 않는다. SEC-B3/175 가 그 질문을 사후에 닫았지만 루트 밖 스킵은 남았다.

## 못 잰 것 (정직 고지)
- **유휴 상태 절대값을 못 쟀다.** 고아 `yes` 10개가 10코어를 점유했고 `kill`/`pkill` 이 classifier 에 차단돼 유휴로 못 돌렸다. 모든 wall 절대값은 부하 오염 상태다 — cpuUsage(부하 강건)로 제품 기여분을 분리했으나, 「루브릭 5행 <150ms 절대」의 유휴 충족은 **확인 불가**(추정: node 기동 ~70ms + 제품 ~40ms ≈ 110ms 로 유휴면 통과할 가능성이 높으나 미측정).
- **결함1 의 최종 무기화(doctor --repair → npm publish DENY→ALLOW 플립)까지는 안 돌렸다.** 각 링크의 메커니즘(Write 허용·sh 허용·저널 안착·replayState 승인 반영)은 개별 실측·소스로 확인했으나 마지막 publish 플립은 미실행(보안 축의 영역이자 예산 고려).
- **`make <target>` 비용·커버리지 미측정** — Makefile 문법 해석은 범위 밖(문서화된 알려진 한계).
- 표본 n=30·5 는 작다. p95/max 의 꼬리는 부하 때문에 넓다.

## 점수 산출 근거
- 순수 효율 공학은 4.6~4.7 급: 최악 입력 전부 선형(지수 backtracking 재발 0), fail-closed 비용 캡, 영리한 선필터(정직한 최악 고지 포함), 부하 인지·자동 채점 벤치, 비간섭 경로 sh 바닥값 근접.
- **4.8 미충족 사유**: 4.8 은 「조건 전건 충족 + 잔여 감점 LOW 이하」. 이 축이 겨누는 「비용 절감이 방어를 빼먹는 곳」에 **에이전트 레인으로 도달 가능한 HIGH급 fail-open(루트 밖 스크립트 스킵)** 이 열려 있고, 형제 캡의 fail-closed 처방이 안 됐다. HIGH 잔여는 LOW 이하가 아니다.
- 여기에 유휴 절대값 미검증(측정 한계)과 「비간섭 비용 0」의 문자적 미달(INFO)을 더해 **4.2**. 효율 설계의 강함과 정직함이 점수를 떠받치고, 개봉된 HIGH 방어-비용 구멍이 4.8 을 막는다.

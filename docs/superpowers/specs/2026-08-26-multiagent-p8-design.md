# 멀티에이전트 P8 오케스트레이션 — 설계 v2 (A안: 워크트리 격리)

- 상태: 초안 v2 (독립 리뷰 REWORK 반영 — BLOCKER 2·MAJOR 5·MINOR 6). 사용자 리뷰 대기.
- 결정 확정: 결과물 = **제품 + 운영 둘 다** · 목적 = **처리량 + 난이도별 모델 + 구현자≠검증자** 셋 다 · 격리 = **A안(워크트리)** · **코어(core/src) 무변경**.
- v1→v2 핵심: ① `.harness/` 격리를 «실측 사실»에서 **집행 전제조건**으로 격하 ② 회계 순서를 **선-create → 병렬 → 머지 → 후-정산**으로 재작성 ③ 신뢰경계를 **세션 전역 훅 가드**(워커도 가드됨)로 정정.
- 관련: `.claude/CLAUDE.md`(모델 라우팅), `skills/phase-p8-implement/SKILL.md`, `agents/wave-executor.md`·`wave-verifier.md`, `core/src/wave.ts`·`loop.ts`·`cli.ts`, `superpowers:dispatching-parallel-agents`·`using-git-worktrees`.

## 1. 문제와 목표

현재 P8(구현)은 **순차**로 진행한다. 코어의 `state.activeWave` 는 하나만 둘 수 있고(`wave.ts:204` — 이미 활성 웨이브가 있으면 activate 를 거부한다), 메인 세션은 한 웨이브를 `create → activate → loop brief → wave-executor → loop attempt → wave update → complete` 순서로 처리한 뒤 다음 웨이브로 넘어간다.

목표는 세 가지다. **독립 웨이브를 병렬로 구현**해 처리량을 늘리고, 난이도에 맞는 모델을 골라 비용과 품질을 맞추고, 구현자와 검증자를 나눈다(OPS-74). 다만 **코어 저널의 무결성(SEC-49~318)을 지키려고, 저널에 동시에 쓰는 구조는 만들지 않는다.**

원칙: **느린 작업은 병렬로, 가벼운 작업은 순차로 처리한다.** 오래 걸리는 구현·테스트는 워크트리마다 둔 워커가 병렬로 맡는다. 회계 작업(웨이브 create/complete·저널·RTM·STALE)은 빨리 끝나고, 정본 `.harness/` 에 쓰는 주체가 하나여야 한다. 그래서 오케스트레이터가 순차로 맡는다.

### 1.1 두 전제 — «사실»이 아니라 «집행 전제조건»이다 (v2 정정: BLOCKER-1)

v1 은 「`.harness/` 는 git 이 추적하지 않으므로 워크트리 격리에 드는 비용이 없다」를 실측 사실로 적었는데, 이것은 **틀렸다.** 코어는 정반대를 문서화한다: `wave.ts:116`·`loop.ts:16` 「`.harness/` 는 git 커밋 대상이라 브랜치를 전환하면 events.jsonl 이 되감긴다」, `state.ts:98-101` 은 `.harness/.runtime/` **안에만** gitignore 를 둔다(=`.runtime/` 만 빼고 커밋). `nextWaveId` 이중최댓값·잔존증적 가드(`wave.ts:109-118,177-189`)·`migrate.ts:140-142` 는 모두 「커밋된 `.harness/` 가 브랜치와 함께 되감기는」 상황을 전제로 둔 방어 장치다.

→ 워크트리 격리는 **대상 리포에서 `.harness/` 가 gitignore 되어 있을 때만** 성립한다(그래야 `git worktree add` 가 `.harness/` 사본을 안 만들고, 회계와 코드가 다른 브랜치로 갈라지지 않는다). 이를 **`phase-p8-orchestrate` 0단계에서 강제 검사**한다(아래 §6.0). 그리고 이 요구가 코어 주석과 모순되므로, **하네스 공식 스탠스**(병렬 오케스트레이션에서는 `.harness/` = 로컬/gitignored)를 이 문서로 못박고, 코어 주석과의 불일치를 「알려진 긴장」으로 명시한다. 그래야 두 문서의 내용이 서로 반대인 채로 플랜에 넘어가지 않는다.

## 2. 흐름 (v2: 선-create → 병렬 → 머지 → 후-정산 · BLOCKER-2)

v1 은 회계(`wave create`)를 **머지 후**로 미뤘다. 그러면 네 가지 문제가 생긴다. 워커에 줄 브리프가 없다(`loop brief` 는 디스크의 지시서를 읽는다 `loop.ts:583`). 유령 참조 검증이 구현 뒤로 밀린다(`createWave` 는 없는 refs 를 거부한다 `wave.ts:152`). 증적 id 가 없다(id 는 create 가 발급한다 `wave.ts:120-136`). 크래시가 나면 정본에 흔적이 남지 않아 재개할 수 없다(`loop.ts:7` 연속성 계약 위반). 그래서 v2 는 순서를 뒤집는다:

```
Fable 오케스트레이터  (메인 세션 · 정본 .harness/ 소유 · 세션 전역 훅 가드 안)
  │
  ├─ (P8 진입) 0단계 전제조건 검사(§6.0) → 승인설계(F/M/SCH)에서 «웨이브 플랜» 산출
  │     각 웨이브 = { goal, refs, accept, fileScope(파생·§3), difficulty(§4), round }
  │     의존/충돌 그래프 → 위상 «라운드»로 분할 · 계약/생성파일은 라운드 선두 «계약 웨이브」로(§3)
  │
  └─ 라운드마다:
        1. [선-create] 라운드 웨이브들을 **순차 `wave create`** — id 발급·유령참조 사전검증·지시서 디스크 기록
             (create 는 activeWave 불변 → pending 다발 공존, 게이트 없음. wave.ts:138-200)
        2. [브리프] `harness loop brief <id>` 로 **코어가 만든 펜스 브리프**(nonce·sanitizeUntrusted, SEC-28)를
             각 워커에 전달 — 오케스트레이터 수제 브리프 금지(보안 회귀). buildExecutorBrief 는 active 불요(loop.ts:583)
        3. [병렬 구현] 워크트리별 wave-executor **병렬 디스패치**(난이도별 모델·워크트리경로·파일스코프)
             — 병렬 모드: 워커는 harness 명령 없이 «구현만», 턴로그는 scratchpad/<id>.md (§6.2)
        4. [검증] 웨이브별 신규 컨텍스트 wave-verifier(같은 워크트리)로 인수기준 판정 → pass/fail
             검증 결과는 도착 순서대로 오케스트레이터가 `loop attempt` 기록(recordAttempt active 불요, loop.ts:196)
        5. [머지] pass 웨이브 브랜치를 통합브랜치에 머지
        6. [통합검증] **머지 후·회계 전** 통합브랜치에서 전체 스위트 1회(§5, MAJOR-3) — 실패=충돌 취급
        7. [후-정산] 웨이브별 순차: activate → 증적 복사 → wave update(턴로그) → complete
             (증적: create 는 증적 디렉토리에 파일이 미리 있으면 거부하므로 순서는 create→복사→complete. wave.ts:177-189)
```

순서만 이렇게 바꾸면 네 가지가 함께 성립한다. 브리프의 보안, 유령 참조를 검증하는 시점, 증적 id 의 정합, 크래시 뒤 재개(지시서와 attempt 가 저널에 남아 있다)다. 그러면서 **코어 diff 0** 을 유지한다.

## 3. 웨이브 분해 · 독립성 (처리량의 핵심)

### 3.1 파일 스코프 파생
코어의 노드·웨이브 모델에는 path-scope 필드가 없다(`LedgerNode`·`WaveMeta` 확인). 그래서 오케스트레이터가 설계 산출물과 리포 구조를 보고 각 웨이브의 파일 스코프를 추정한다. 근거로 쓰는 것은 P2 `02-module.md`(모듈 경계·의존 그래프), P5 `05-contract`(SCH/API 가 닿는 파일), `.codesight`(영향이 큰 파일·의존 그래프)다.

### 3.2 독립성 판정
두 웨이브는 파일 스코프가 서로소이고 산출물 사이에 의존이 없을 때만 병렬로 돌려도 안전하다. 스코프가 겹치거나 의존이 있으면 다른 라운드로 나눠 직렬로 처리한다.

### 3.3 계약/생성 파일 클래스 — 구조적 상수 (v2: MAJOR-4)
여러 웨이브가 함께 쓰는 고임팩트 파일 말고도, **내용이 한 파일에 모이는 계약·생성 파일** 때문에 병렬로 돌릴 수 있는 범위가 크게 줄어든다: `schema.prisma`(23모델 단일 파일)·순서 있는 마이그레이션 디렉토리·`package-lock.json`·배럴(`index.ts`). 이것은 «분해 오류»가 아니라 구조상 피할 수 없는 조건이다. 처리 방법은 다음과 같다:
- **스키마·마이그레이션 변경**: 라운드 선두의 전용 **«계약 웨이브» 하나**로 몰고, 나머지 웨이브는 그 결과 위에서 병렬로 진행한다(계약 웨이브는 그 라운드에서 단독으로 돈다).
- **락파일**: 웨이브별로 만지지 말고, 머지 시 `npm install` 재실행으로 **기계로 재생성**한다(충돌은 사람이나 오케스트레이터가 손으로 고치지 않고 도구로 해소한다).
- **배럴/생성 파일**: 스코프에 명시하고 계약 웨이브 부류로 다룬다.

### 3.4 라운드 구성
의존 그래프를 위상 정렬해 라운드를 나눈다. 같은 라운드 안에서 서로소인 웨이브는 병렬로, 라운드끼리는 순차로 진행한다(앞 라운드의 통합 결과가 뒷 라운드의 base 가 된다). 사이클이 있거나 판단이 모호하면 **보수적으로 직렬화**한다.

### 3.5 산출물
«웨이브 플랜»은 사람이 읽는 산출물로 남긴다(스크래치 또는 오케스트레이터 로컬): `waveId·refs·accept·fileScope·difficulty·round·class(계약/일반)`. 코어 밖에 두는 계획 문서다.

## 5. 머지 · 충돌 전략

- **통합 브랜치 경유**(main 직접 아님): 라운드 결과를 `integration/p8-<milestone>` 위에 차례로 쌓고, 마일스톤 전체가 초록이면 main 으로 보낸다.
- **라운드 내 머지**: 스코프가 서로소라서 파일 충돌은 0건으로 예상한다. 머지 순서는 정하지 않는다.
- **머지 후 통합 검증**(v2: MAJOR-3): 라운드 모든 머지 후·정본 회계 **전에** 통합브랜치에서 **전체 스위트 1회**. 파일 스코프가 서로소여도 «의미 충돌»(A가 헬퍼 계약을 바꾸고 B가 새 호출자를 추가하면, 각자는 초록인데 합치면 빨강)은 막을 수 없다. 그래서 라운드마다 확인한다(마지막에 몰아서 확인하면 원인을 가려내는 비용이 커진다). 실패하면 충돌로 취급한다.
- **충돌 처리**: ① 락파일류는 기계 재생성(§3.3) ② 그 외는 갱신된 base 에 **재디스패치**(오케스트레이터의 수제 해소 편집 금지 — 그 diff 는 어느 장부에도 기록되지 않아, P8 의 변경과 노드 사이의 대응이 끊긴다. v2: MINOR-5). 재디스패치로도 풀리지 않으면 두 웨이브를 합쳐 직렬로 처리한다.
- **후-정산 타이밍**: 통합 검증이 초록이 된 뒤에 웨이브마다 순차로 `activate→증적복사→update→complete` 를 실행한다. 그래서 코어에 동시에 쓰는 일이 없다.
- **3-strike**(v2: MINOR-4): 3회 연속 실패한 웨이브는 사용자를 소환한다. **소환 웨이브의 후속 의존 웨이브는 보류, 비의존 라운드는 진행**(명문화).

## 6. 오케스트레이션 기계장치 · 신뢰경계

### 6.0 0단계 전제조건 검사 (v2: BLOCKER-1)
`phase-p8-orchestrate` 에 들어가자마자 `git ls-files .harness` 가 비어 있고 `.gitignore` 에 `.harness/` 가 있는지 검사한다. 조건이 맞지 않으면 **중단하고 사용자가 결정**하게 한다(gitignore 추가 후 재개 / 병렬 모드를 포기하고 순차 p8-implement). 이때 이유와 명령을 사용자에게 보여 준다.

### 6.1 신뢰경계 — 세션 전역 훅 가드 (v2 정정: MAJOR-1)
**「워커 무가드」는 거짓이었다.** `hooks/hooks.json` 의 PreToolUse/PostToolUse 는 **세션 전역** 매처라서 서브에이전트(Agent tool)의 도구 호출에도 실행된다(리뷰에서 실증했다). 가드 대상 판정은 경로 기반이고 루트 = `CLAUDE_PROJECT_DIR ?? cwd`(`cli.ts:1649`) = 정본 루트. 즉 **워커가 어느 워크트리에 있든 정본 `.harness/**` 쓰기는 오늘과 동일하게 가드된다** — 이는 A안에 유리한 정정이다(무가드 절충은 애초에 없었고, C안의 주 명분도 사라진다). 남는 한계도 적어 둔다. 빌드 트랙에서는 워커의 «소스» 쓰기가 허용되므로, 워커가 정본 소스 트리를 고칠 수 있다. 이것은 **파일 스코프 규율(프롬프트)로만** 막는다.

### 6.2 wave-executor 병렬 모드 정의 (v2: MAJOR-2 — 결과물 항목)
현행 `agents/wave-executor.md` 철칙 3 「매 턴 `harness wave update`」는 병렬 모드에서 **정본 저널을 오염**시킨다(`harness` 는 `CLAUDE_PROJECT_DIR` 로 정본 위치를 정하므로, 워크트리 cwd 에서 실행해도 정본에 기록된다 `cli.ts:1649`. 라운드 중 정본에 활성 웨이브가 없으면 오류가 나고, 있으면 다른 웨이브의 턴 로그에 병렬로 기록된다). → **병렬 모드에서 워커는 `harness` 명령 전면 금지, 턴로그는 `scratchpad/<waveId>.md`.** 별도 에이전트(`wave-executor-parallel`)로 분리하거나 브리프 모드 플래그로 명문화(현 설계가 이미 있는 것처럼 서술한 규칙을 실제로 적는다). wave-verifier 의 `harness status`/`trace` 질의도 같은 방식으로 정본을 가리키므로, 병렬 모드에서는 워크트리 로컬 정보만 쓰도록 조정한다.

### 6.3 워크트리 메커니즘 결정 (v2: MAJOR-5)
인용한 `superpowers:using-git-worktrees` 는 「네이티브 워크트리 도구가 있으면 수동 `git worktree add` 금지(#1 실수)」라 못박는다. 네이티브 둘: `EnterWorktree` 도구, Agent tool `isolation:"worktree"`. **결정: Agent `isolation:"worktree"` 우선** — 워커를 디스패치하면 워크트리가 자동으로 생기고, 변경이 없으면 자동으로 정리된다. 다만 검증자가 실행자와 **같은 워크트리**를 써야 한다(§2 step 4). 그래서 실행자는 보고에 워크트리 경로를 넣고, 검증자는 isolation 없이 그 경로로 들어간다. 변경이 있는 워크트리는 남으므로, 그 수명 주기를 확인하고 정리하는 방법을 운영 노트에 적는다. (선행 `.claude/worktrees/wf_*` 4개 잔여는 이 네이티브 도구가 남긴 것 — dogfood 전 정리.)

### 6.4 스킬 구조 (v2: MINOR-3)
신규 `phase-p8-orchestrate` 는 기존 `phase-p8-implement`(단일 웨이브 원자 절차)를 **위에서 조율**(스킬이 절차 문서이므로 orchestrate 가 회계 구간에서 p8-implement 절차를 그대로 수행 — 구조상 문제없음). **트리거 배타화**: orchestrate 는 «병렬·다웨이브» 신호에만 반응하게 하고, p8-implement description 에는 상호 참조 한 줄을 넣는다. 웨이브가 하나뿐인 프로젝트는 과설계를 피하려고 p8-implement 로 폴백한다. 병렬 디스패치에는 `superpowers:dispatching-parallel-agents` 를 활용한다.

## 8. Dogfood 계획

먼저 이 리포의 다음 빌드 작업에 적용해 검증한 뒤 제품 스킬로 확정한다. 다만 §6.0 전제조건(`.harness/` gitignore)을 충족해야 한다. 그리고 이 리포는 지금 설계/보안 트랙이라서 실제로 병렬 P8 을 dogfood 할 웨이브가 마땅치 않을 수 있다 → dogfood 대상은 따로 협의한다(작은 독립 개선 2~3건을 인위적 병렬 라운드로). → **결정(2026-08-26): 인위적 라운드 구성** — 이 리포는 병렬 P8 대상이 아니므로(자기 미적용·설계 트랙), 별도 샌드박스에 `harness init` + `.harness/` gitignore 후 독립 개선 2~3건을 인위적 병렬 라운드로 꾸며 end-to-end 검증한다. **실행은 후속 작업**(샌드박스 구성 + phase-p8-orchestrate 실구동). **워크트리 비용 주의**(v2: MINOR-1): 리포 안 `.claude/worktrees/` 에 체크아웃이 N개 생기면, 메인의 전역 glob(테스트·린트·grep)이 사본까지 대상에 넣을 수 있다(러너의 exclude 확인 필요). next-app 이면 워크트리마다 `npm install`(분·GB × N)을 돌려야 해서 처리량 이득이 사라진다 → pnpm/캐시를 공유하거나 워크트리를 재사용한다.

## 9. 위험 · 미해결

- **`.harness/` 스탠스 긴장**(BLOCKER-1): 코어 주석(커밋)과 오케스트레이션 요구(gitignore)가 반대다. §1.1 에서 병렬 모드는 gitignore 로 못박았지만, 하네스 전체의 공식 스탠스는 아직 열린 항목이었다. → **결정(2026-08-26): A — 커밋된 `.harness/` 를 하네스 기본으로 유지**(브랜치 이동·PR 리뷰 이점, 잔존증적/nextWaveId 가드가 방어하는 세계). gitignore 는 병렬 모드 전용(§6.0 게이트)으로, 긴장은 「모드별 요구」로 확정 — 전역 스탠스는 바꾸지 않고 코어 주석도 그대로.
- **의미 충돌**: 스코프가 서로소여도 막을 수 없다 → §5 의 라운드 통합 검증으로 줄이고, 남는 것은 마일스톤 검증에서 잡는다.
- **분해 정확도**: 파일 스코프를 잘못 추정하면 통합 검증이 실패하고, 그러면 재디스패치한다.
- **워커 소스 규율**: 워커도 가드를 받지만, 정본 소스 트리에 쓰는 일은 파일 스코프를 지키라는 프롬프트 규율로만 막는다(§6.1).
- **dogfood 대상·워크트리 install 비용**(§8).

## 10. Non-goals

- 코어에 활성 웨이브를 N개 두는 B안 — 저널에 동시에 쓰는 위험이 있어 제외한다.
- C안(워커별 `harness init`) — 「워커도 가드」는 §6.1 정정으로 A안에서 이미 성립하고, C안은 워크트리 로컬 저널 머지백 문제(버리면 유실·합치면 B안 동시쓰기)라는 더 나쁜 문제. 선-create(§2)가 C안 잔여 이점(지시서 실존·재개성)을 코어 무변경으로 흡수. **C안 필요 지점 없음.**
- 하네스 자동 에이전트 디스패치 — 디스패치는 메인 세션(스킬)이 맡는다.
- 난이도 채점 ML — 규칙표로 충분하다.

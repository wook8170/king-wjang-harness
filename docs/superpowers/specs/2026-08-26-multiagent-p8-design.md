# 멀티에이전트 P8 오케스트레이션 — 설계 (A안: 워크트리 격리)

- 상태: 초안 (사용자 리뷰 대기)
- 결정 확정: 결과물 = **제품 + 운영 둘 다** · 목적 = **처리량 + 난이도별 모델 + 구현자≠검증자** 셋 다 · 격리 = **A안(워크트리 FS 격리, 워커 무가드)** · **코어(core/src) 무변경**
- 관련: `.claude/CLAUDE.md`(모델 라우팅 정책), `skills/phase-p8-implement/SKILL.md`, `agents/wave-executor.md`, `agents/wave-verifier.md`, `superpowers:dispatching-parallel-agents`

## 1. 문제와 목표

현재 P8(구현)은 **순차**다: 코어의 `state.activeWave` 가 단수이고(`core/src/wave.ts:204` — 이미 활성이면 activate 거부), 메인 세션이 웨이브 하나를 `create → activate → loop brief → wave-executor 디스패치 → loop attempt → wave update → complete` 로 돌린 뒤 다음 웨이브로 간다. 독립적인 웨이브들이 있어도 한 번에 하나씩만 구현된다.

목표: **독립 웨이브를 병렬로 구현**해 전체 구현 시간을 줄이고(처리량), 웨이브 난이도에 맞춰 모델을 배분하며(비용/품질), 구현자와 검증자를 분리(OPS-74)한 채로 이를 달성한다. **코어의 저널 무결성(SEC-49~316)은 절대 동시쓰기로 만들지 않는다.**

핵심 원리: **느린 것은 병렬, 싼 것은 순차.** 구현·테스트(느림)는 워크트리별 워커가 병렬로. 회계(웨이브 create/complete·저널 append·RTM·STALE 전파 — 빠름)는 오케스트레이터가 **정본 `.harness/` 하나에서 순차로**.

### 이를 가능케 하는 실측 사실
- `.harness/` 는 **git 미추적**(gitignore 도 tracked 도 아닌 순수 로컬 상태). → `git worktree add` 로 만든 워크트리는 자기 `.harness/` 를 물려받지 않고, 워커별 상태가 git 병합 대상이 아니다. **쓰기 격리가 공짜**이고 회계 병합 충돌이 없다.
- 코어 노드 모델(`LedgerNode = {id,title,parent?,doc_anchor?,version,status}`)·웨이브 모델(`WaveMeta = {id,milestone,design_refs,status,acceptance}`)에는 **path-scope·난이도 필드가 없다.** → 파일 스코프와 난이도는 **오케스트레이터가 설계 산출물에서 파생**한다(코어는 무변경, 웨이브를 순차 기록만).

## 2. 아키텍처

```
Fable 오케스트레이터  (메인 세션 · 정본 .harness/ 소유 · 하네스 훅으로 가드됨)
  │
  ├─ (P8 진입) 승인된 설계(F-x 피처, M-x 모듈, 05-contract)에서 «웨이브 플랜» 산출
  │     각 웨이브 = { goal, refs(F-x…), accept(P3 기준), fileScope(파생), difficulty(파생), round }
  │     의존/충돌 그래프 → 위상 «라운드»로 분할 (한 라운드 = 파일스코프 서로소 = 병렬안전)
  │
  └─ 라운드마다:
        1. 각 웨이브에 git worktree + 브랜치 생성 (wave/<id>)
        2. wave-executor N개 병렬 디스패치 — 난이도별 모델, 브리프+워크트리경로+파일스코프
             (워커는 워크트리 FS 안에서만 작업 · .harness/ 없음 · 하네스 가드 없음)
        3. 각 웨이브: 신규 컨텍스트 wave-verifier(같은 워크트리)로 인수기준 판정 → pass/fail
        4. pass → 오케스트레이터가 브랜치를 통합브랜치에 머지
        5. 라운드 종료 후: 오케스트레이터가 정본 .harness/ 에 그 라운드 웨이브들을
             harness wave create→activate→loop attempt→complete 로 **순차 기록**
```

**신뢰 경계**: 저널·게이트를 위조할 수 있는 표면은 오직 **가드된 오케스트레이터 세션**뿐(오늘과 동일). 워커는 자기 워크트리 밖(정본 `.harness/`)을 상대경로로 건드릴 수 없고, 오케스트레이터는 워커에게 정본 루트 경로를 주지 않는다. 워커가 코드를 구현하는 것은 «출하 트랙에서 원래 허용된 소스 쓰기»라 무가드가 실효 손실이 작고, **wave-verifier 게이트가 뒤를 받친다**.

## 3. 웨이브 분해 · 독립성 (처리량의 핵심)

### 3.1 파일 스코프 파생
코어에 모듈→경로 매핑이 없으므로 오케스트레이터가 **설계 산출물 + 리포 구조**로 각 웨이브의 파일 스코프(touch 예상 경로 집합)를 추정한다:
- **1차 출처: P2 `02-module.md`** — 모듈 경계·의존그래프가 산문/표로 있다. 웨이브의 `--refs` 가 가리키는 F-x/M-x → 그 모듈의 경로 프리픽스(예: `src/order/**`, `src/lib/db.ts`).
- **2차 출처: P5 `05-contract`(SCH/API)** — 스키마·API 변경이 닿는 파일.
- **보정: 리포 구조** — `.codesight/` 의 high-impact 파일 목록(예: `src/lib/db.ts` 78곳 임포트)으로 «공유 고임팩트 파일» 식별.

### 3.2 독립성 판정
두 웨이브가 **병렬안전 ⟺ 파일스코프 서로소 AND 산출 의존 없음**:
- **파일 겹침**: 스코프 교집합 ≠ ∅ 면 충돌 → 직렬화(다른 라운드). 특히 공유 고임팩트 파일(`db.ts`·`utils.ts`·`page-header.tsx` 등)을 둘 이상이 건드리면 그 웨이브들은 순차.
- **산출 의존**: 웨이브 B 가 웨이브 A 가 만드는 심볼/파일을 임포트하면 A→B 순서. `--refs` 의 설계 의존(부모/`doc_anchor`)과 `.codesight` 의존그래프로 추정.

### 3.3 라운드 구성
의존그래프를 위상정렬해 **라운드(위상 레이어)** 로 나눈다. 라운드 내부는 서로소라 병렬. 라운드 간은 순차(앞 라운드 머지가 뒷 라운드 base). 사이클/모호하면 **보수적으로 직렬화**(과병렬로 인한 충돌보다 안전).

### 3.4 산출물
오케스트레이터가 «웨이브 플랜»을 사람이 읽을 산출물로 남긴다(예: 스크래치 `wave-plan.md` 또는 오케스트레이터 로컬). 각 행: `waveId · refs · accept · fileScope · difficulty · round`. 이건 **코어 밖 계획 문서**다(코어는 무변경).

## 4. 난이도 → 모델 루브릭

오케스트레이터가 웨이브별로 채점(코어 필드 아님, 플랜 시점 파생). `.claude/CLAUDE.md` 모델 정책과 정렬:

| 난이도 | 신호 | 구현 모델 | 검증 모델 |
|---|---|---|---|
| **Trivial/기계적** | 스코프 1~2파일 · 고임팩트 무접촉 · 스펙 완전확정(문자열치환·이름변경·import정리·표/문서) | Haiku 4.5 | Haiku/Sonnet |
| **Clear-spec** | 스코프 소~중 · 단일 모듈 내 · 인수기준 명확 · 신규성 낮음 | Sonnet 5 | Sonnet 5 |
| **Multi-file/통합/미묘** | 다파일·다모듈 걸침 · 고임팩트 파일 접촉 · 트레이드오프/미묘한 로직 · 신규성 높음 | Opus 4.8 | Opus 4.8 |

- **오케스트레이터 자신**: Fable 5(소진 시 Opus 4.8) — 설계·플랜·분해·취합.
- **경계 원칙**(CLAUDE.md): 설계·트레이드오프·다파일 통합·미묘한 수정은 Haiku 로 내리지 않는다. 애매하면 한 단계 위(Sonnet). Haiku 는 «무엇을·어디를·어떻게»가 이미 확정된 저위험만.
- **검증자는 항상 구현자와 다른 신규 컨텍스트**(OPS-74) — 모델은 웨이브 복잡도 매칭(대개 Sonnet, 통합웨이브 Opus). 검증자에겐 «이 인수기준을 반증하라»를 준다.
- 채점은 **루브릭(규칙표)** 이지 학습모델이 아니다 — 오케스트레이터가 위 신호로 한 단계 배정하고, 실패(아래 3-strike) 시 한 단계 승급.

## 5. 머지 · 충돌 전략

- **통합 브랜치 경유**(main 직접 아님): 라운드들이 `integration/p8-<milestone>` 위에 쌓이고, 마일스톤 전체가 초록이면 그때 main 으로. 롤백이 쉽고 부분 실패가 main 을 더럽히지 않는다.
- **라운드 내 머지**: 스코프 서로소라 무충돌 기대. 순서는 임의(서로소니까).
- **라운드 간**: 앞 라운드 통합 결과가 뒷 라운드 워크트리의 base. 뒷 라운드 워크트리는 **앞 라운드 머지 후 생성**(최신 base 위에서 구현 → 리베이스 충돌 최소).
- **충돌 처리**(분해가 불완전했다는 신호): ① 자명하면 오케스트레이터가 해소 후 재검증 ② 아니면 그 웨이브를 **갱신된 base 에 재디스패치**(리베이스 후 재구현) ③ 반복 충돌은 두 웨이브를 병합해 한 웨이브로 직렬화. **충돌=분해 오류**로 취급해 다음 플랜에 반영.
- **정본 회계 타이밍**: 머지가 **끝난 뒤** 오케스트레이터가 `wave create/activate/loop attempt/complete` 를 순차 실행 → 코어 동시성 0. 즉 정본 `.harness/` 는 «이미 머지된 사실»을 기록할 뿐, 병렬 구현 도중엔 안 건드린다.
- **3연속 실패**: 기존 규칙 유지(웨이브별, 기본 임계 3) — 한 웨이브가 3회 실패하면 그 웨이브만 사용자 소환, 나머지 라운드는 계속.

## 6. 오케스트레이션 기계장치

**실측**: 하네스는 에이전트를 «자동 디스패치» 하지 않는다 — 메인 세션이 스킬대로 wave-executor/wave-verifier 를 부른다. 그러므로 이 재설계의 본체는 **오케스트레이션 층(스킬 + 에이전트 정의 + 디스패치 패턴)**이고, 코어 코드가 아니다.

- **신규 스킬 `phase-p8-orchestrate`** — 기존 `phase-p8-implement`(단일 웨이브 원자 절차)를 **위에서 조율**. 절차: 웨이브 플랜 산출 → 라운드 루프 → (라운드마다) 워크트리 생성·병렬 디스패치·검증·머지 → 정본 순차 기록. 단일 웨이브 프로젝트는 기존 p8-implement 로 폴백(과설계 방지).
- **병렬 디스패치**: `superpowers:dispatching-parallel-agents` + `superpowers:using-git-worktrees` 활용. 워크트리는 `.claude/worktrees/wave-<id>` 관례(선행 `wf_*` 잔여는 정리 대상). 각 디스패치에 **모델 파라미터**(Agent tool `model`)를 난이도 루브릭대로 지정.
- **wave-executor 정의 보강**: 입력에 «워크트리 경로 + 파일스코프 + 시트». 워커는 스코프 밖을 건드리지 않는다(오늘의 «시트 밖 금지» 규칙 유지, 이제 물리적 워크트리 경계로도 강제). 보고는 `scratchpad/<waveId>.md`.
- **wave-verifier 정의**: 거의 그대로. 같은 워크트리에서 인수기준 실행, 신규 컨텍스트, 판정만.
- **취합**: 오케스트레이터가 워커/검증자 보고를 `scratchpad/*.md` 로 받아 필요한 줄만 grep(간결 모드 정합).

## 8. Dogfood 계획 (운영 → 제품 순)

이 리포(king-wjang-harness) 자신의 다음 빌드 작업에 먼저 적용해 검증한 뒤 제품 스킬로 확정한다. 단, **이 리포는 지금 설계/보안 트랙**이라 실제 P8 병렬 dogfood 대상 웨이브가 마땅치 않을 수 있음 → dogfood 대상은 별도 협의(작은 독립 개선 2~3건을 인위적 병렬 라운드로).

## 9. 위험 · 미해결

- **분해 정확도**: 파일스코프를 설계문서에서 «추정»하므로 틀리면 머지 충돌. 완화: 충돌=재디스패치(§5), 보수적 직렬화(§3.3). 잔여 위험: 초기엔 과직렬화(안전하나 처리량 이득 축소) → 경험으로 조정.
- **워커 무가드**: A안의 의도된 절충. 워커가 정본 `.harness/` 를 절대경로로 건드릴 이론적 여지 → 오케스트레이터가 루트 경로 미전달 + 워크트리 경계로 완화. C안(워커도 자기 `harness init`)으로 승급은 «워커도 완전한 P8 규율»이 필요할 때 별도 결정.
- **비결정 병렬**: 여러 워커 동시 실행의 로그·비용 관측. 완화: 보고를 `scratchpad/<waveId>.md` 로 표준화.
- **선행 워크트리 잔여**: `.claude/worktrees/wf_28bae004-*` 4개 — dogfood 전 정리.

## 10. Non-goals

- 코어를 N-활성웨이브로 확장(B안) — 저널 무결성 동시쓰기 위험으로 제외.
- 하네스가 에이전트를 «자동» 디스패치하게 만드는 것 — 디스패치는 메인 세션(스킬)이 한다는 현 모델 유지.
- 난이도 채점의 ML 화 — 규칙표 루브릭으로 충분.
